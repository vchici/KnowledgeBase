# 图片尺寸与组件不匹配

> **本质**:「不匹配」要拆成两层看——**解码层**(内存里 Bitmap 的 px 尺寸 vs 实际显示需要的大小)决定**内存与清晰度**;**布局层**(ScaleType 如何把 Bitmap 塞进 View)决定**视觉结果**。两层都失控,OOM、模糊、变形三者至少占一个,且经常同时出现。

## 三种维度的"不匹配"

| 维度 | 例子 | 直接后果 |
| --- | --- | --- |
| **像素尺寸不匹配** | 4000×3000 的图显示在 300×300 的 View | 内存浪费 ~100×,纹理上传卡顿,可能 OOM |
| **宽高比不匹配** | 16:9 的图显示在 1:1 的 View | 变形 / 裁剪 / 留白,取决于 ScaleType |
| **密度不匹配** | 图放在 `drawable-mdpi`,设备是 xxhdpi | 解码时自动放大 3 倍,内存 ×9 |

## 三个容易混淆的"尺寸"

```text
Bitmap 尺寸(px)         Drawable intrinsic 尺寸        View 尺寸(px)
内存里真实的像素大小  →  BitmapDrawable 直接透传    →  measure/layout 后才确定
决定内存与清晰度         Bitmap.getWidth()              决定绘制区域
```

- `Bitmap.getWidth()/getHeight()`:解码产物,受 inSampleSize、密度缩放影响。
- `Drawable.getIntrinsicWidth()`:BitmapDrawable 等于 Bitmap 尺寸;九宫格、Shape 另算。`wrap_content` 的 View 用它当参考。
- `View` 的最终尺寸:layout 结束才确定,**在这之前加载库不知道该解码多大**——Glide 的解法是等 measure 完成后再发起解码。

## 解码层:Bitmap 应该多大

### 自动密度缩放(最容易踩的坑)

`decodeResource` 默认 `inScaled = true`,解码尺寸按 **屏幕 dpi ÷ 资源目录 dpi** 缩放:

| 资源目录 | 100×100 原图在 xxhdpi(480dpi)设备上解码为 | 内存 |
| --- | --- | --- |
| drawable-xxhdpi | 100×100 | 1× |
| drawable-mdpi(放错) | 300×300 | **9×** |
| drawable-nodpi | 100×100(不缩放) | 1× |

### inSampleSize:手动下采样

```java
// 两步走:先探尺寸(不分配像素),再算采样率
val options = BitmapFactory.Options().apply { inJustDecodeBounds = true }
BitmapFactory.decodeResource(resources, R.drawable.big, options)

options.inSampleSize = calcInSampleSize(options, reqWidth, reqHeight) // 只允许 2 的幂
options.inJustDecodeBounds = false
val bitmap = BitmapFactory.decodeResource(resources, R.drawable.big, options)
```

- `inSampleSize = 2^n`:宽高各除以 n 档,内存缩小 4^n 倍;解码器内部整行整列丢弃,**快但采样粗糙**。
- 只能取 2 的幂,无法精确对齐目标尺寸(如 3/2 采样),精细缩放要靠绘制阶段。

### Glide 等加载库:自动按目标尺寸解码

```kotlin
// into(view):等 View measure 完,按测量尺寸自动 inSampleSize + 等比缩放
Glide.with(iv).load(url).into(iv)
// 列表/尺寸未定:显式 override,避免按整屏尺寸解码
Glide.with(iv).load(url).override(300, 300).centerCrop().into(iv)
```

不指定目标尺寸时,加载库通常按**屏幕尺寸**解码——列表 item 里一张大图就可能吃掉几十 MB。

## 布局层:ScaleType 决定视觉结果

ScaleType 只回答一个问题:**Bitmap 和 View 尺寸不等时,绘制时怎么变换**(改的是绘制矩阵,不改变 Bitmap 本身的内存占用)。

| ScaleType | 保持宽高比 | 图片 < View | 图片 > View | 一句话记忆 |
| --- | --- | --- | --- | --- |
| `FIT_XY` | 否 | 拉伸铺满 | 压缩铺满 | 铺满即可,允许变形 |
| `FIT_CENTER`(默认) | 是 | **放大**贴合,可能留白 | 缩小完整显示 | 等比 + 完整显示 + 居中 |
| `FIT_START` / `FIT_END` | 是 | 同上,贴顶/贴底 | 同上 | 完整显示,对齐方向不同 |
| `CENTER` | — | 原样居中(不放大) | 原样,超出裁剪 | 我不缩放,裁剪自负 |
| `CENTER_CROP` | 是 | 放大到铺满,居中裁剪 | 等比铺满,裁剪溢出 | 铺满优先,牺牲完整性 |
| `CENTER_INSIDE` | 是 | **原样**(不放大)居中 | 缩小完整显示 | 只缩不放 |
| `MATRIX` | 自定义 | 自定义 | 自定义 | 旋转/手势缩放/换算 |

### 高频混淆:FIT_CENTER vs CENTER_INSIDE

两者在**图片大于 View** 时行为一致(等比缩小完整显示);区别在**图片小于 View** 时:FIT_CENTER 会放大到贴边(可能留白),CENTER_INSIDE 保持原尺寸(显小图清晰不糊)。图标类小图用 FIT_CENTER 会把低分辨率图标拉糊。

### 典型选择

- 头像、封面、海报(宁可裁剪不能露底):`CENTER_CROP` + 固定 `override(w, h)`。
- 整图预览、图表:`FIT_CENTER`。
- 需要平移手势、自定义变换:`MATRIX`(`setScaleType(MATRIX)` 后再 `setImageMatrix`)。

### 背景没有 ScaleType

`View.setBackground()` 的 Drawable 会被**直接拉伸铺满 View(等效 FIT_XY)**,圆角图、非九宫格图当背景必变形。替代方案:

- `.9.png`(NinePatch)指定可拉伸区域;
- `layer-list` / `inset` 控制边距与铺法;
- 或放弃背景,改用 `ImageView`(拥有 ScaleType 能力)。

### 反向匹配:adjustViewBounds

```xml
<ImageView
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:adjustViewBounds="true" />
```

让 ImageView **按图片宽高比反推自己的高度**(要求至少一维是 `wrap_content`),实现图文流的等比卡片。

## 像素级质量后果

| 操作 | 采样算法 | 视觉后果 |
| --- | --- | --- |
| 放大 | 双线性插值(硬件加速默认) | 边缘发虚;不插值则锯齿/马赛克 |
| 缩小 | 采样过滤 | 细节丢失、摩尔纹,缩得太狠直接糊 |
| 非等比缩放 | 横纵不同步 | 宽高比破坏,人脸/图标变形 |

软渲染下需 `Paint.FILTER_BITMAP_FLAG` 才有插值;硬件加速默认开启。**缩放发生在 GPU 采样阶段,成本远低于解码,所以"显示时缩"不省内存——省内存靠解码时下采样。**

## 性能与稳定性后果

1. **OOM**:解码尺寸 > 显示尺寸数倍时,45MB 级 Bitmap 直接打爆内存;Android 8.0 后虽在 native 堆,`getAllocationByteCount()` 照样计入应用占用。
2. **纹理上传卡顿**:过大的纹理吃满 TextureCache(几十 MB 上限)→ 被驱逐 → 每次显示重传 → 列表滑动掉帧。
3. **超 GPU 纹理上限**(`GL_MAX_TEXTURE_SIZE`,常见 4096~16384):纹理创建失败,**图不显示或黑块**;Glide 会自动按上限降采样,手写 BitmapFactory 不会。
4. **HARDWARE Bitmap 限制**:省内存但 `getPixels()`、软件 Canvas、部分变换直接抛异常,混合使用要小心。
5. **列表项尺寸跳动**:尺寸未定时解码,先按整屏解、测量后又重解 → 内存翻倍 + 列表卡顿;固定 `override` 或提前给定尺寸可避免。

## 实践守则

- 一律通过加载库按**目标 View 尺寸**解码;`into(view)` 自动,尺寸未定用 `override` 显式给出。
- 多 density 资源成套提供(或至少 xxhdpi + nodpi 权衡),别让 auto-scale 把小图放大 9 倍。
- 背景:九宫格 / inset,不指望 ScaleType。
- 长图大图:`BitmapRegionDecoder` 分块解码显示。
- 头像封面 `CENTER_CROP` + 固定尺寸;小图标 `FIT_CENTER` 时警惕被放大拉糊。

## 面试高频速答

### 为什么一张 8MB 的图显示在 50dp 的 ImageView 上会 OOM?

<details>
<summary>答案</summary>
OOM 发生在解码阶段而非显示阶段:不指定目标尺寸时,BitmapFactory / 加载库按原图(或整屏 + 密度缩放)解码,4000×3000×4B ≈ 45MB。显示尺寸只影响 ScaleType 绘制矩阵,不影响已解码的内存。解法:inJustDecodeBounds 先探尺寸 → inSampleSize 下采样,或加载库按 View 测量尺寸解码。
</details>

### FIT_CENTER 和 CENTER_CROP 怎么选?

<details>
<summary>答案</summary>
都要完整看到图片内容(图表、截图、预览)选 FIT_CENTER,接受留白;要求区域永远被铺满(头像、封面、Banner)选 CENTER_CROP,接受裁剪。两者都保持宽高比;区别是前者优先完整性,后者优先覆盖性。
</details>

### 缩放是发生在解码时还是绘制时?分别影响什么?

<details>
<summary>答案</summary>
两处都有。解码时:inSampleSize / 密度缩放 / 加载库目标尺寸缩放,改变 Bitmap 的 px 尺寸 → 决定内存占用与纹理上传成本。绘制时:ScaleType / Matrix 变换绘制矩阵,GPU 采样缩放 → 只影响视觉呈现与少量采样开销,不影响内存。省内存靠前者,控观感靠后者。
</details>
