# 线程池在实际工程场景的应用（Java 后端）

> 目的：不背八股，讲清「工程里线程池到底怎么用、为什么这么用、配套哪些知识」。支撑项目包装（异步分析、并发体检）与面试深挖。
> 关联：[synchronized 详解](Lock/synchronized.md)、[Servlet与Tomcat](../JavaWeb/02-Servlet与Tomcat.md)、[Goroutine/GMP](../Go/CSP&GMP.md)、[项目包装-手机性能检测](../FullStack/项目包装-手机性能检测.md)

## 一、为什么需要线程池

- 线程创建/销毁开销大：用户态 ↔ 内核态切换，每个线程栈默认 1MB 内存
- 每请求一线程（Tomcat BIO）在高并发下会打爆资源
- 线程池做三件事：**复用线程**（省创建销毁）、**控制并发度**（避免打爆 CPU/连接）、**排队与拒绝**（削峰）

> 打爆 CPU：线程数 > 核数 → 疯狂上下文切换，CPU 全在「换人」不干活；打爆连接：任务都去抢有限的数据库/下游连接 → 连接耗尽、请求雪崩。线程池靠「并发封顶 + 排队」把同时占用的资源数量变成有上限。

> 一句话：凡是创建销毁成本高的资源，都值得池化 —— 线程池池的是线程，连接池池的是连接，思想同源。

## 二、核心原理：一次任务提交后发生什么

```asciidoc
提交任务 execute(task)
  │
  ▼
线程数 < corePoolSize ？ ──是──▶ 新建 Worker 线程执行
  │否
  ▼
workQueue 能入队 ？ ──是──▶ 排队等待（线程空闲时取出执行）
  │否
  ▼
线程数 < maximumPoolSize ？ ──是──▶ 扩线程执行（最多到 max）
  │否
  ▼
执行拒绝策略 handler
```

注意一个反直觉点：**任务先入队，队列满了才扩线程**，不是直接扩到 max。

### 七个参数

| 参数 | 含义 | 工程要点 |
|------|------|---------|
| corePoolSize | 常驻线程数 | 空闲也不回收 |
| maximumPoolSize | 最大线程数 | 队列满后才扩 |
| keepAliveTime | 非核心线程空闲存活时间 | `allowCoreThreadTimeOut(true)` 可让核心线程也回收 |
| workQueue | 任务队列 | 必须**有界**，选型见下 |
| threadFactory | 线程工厂 | **必须起业务名**，否则 jstack 无从排查 |
| handler | 拒绝策略 | 4 种 + 自定义 |
| unit | 时间单位 | keepAliveTime 的单位 |

### 拒绝策略 4 种

| 策略 | 行为 | 使用场景 |
|------|------|---------|
| AbortPolicy（默认） | 抛 `RejectedExecutionException` | 明确告知调用方失败 |
| CallerRunsPolicy | 谁提交谁执行（降级） | **核心任务常用**：不丢任务，顺势限流 |
| DiscardPolicy | 静默丢弃 | 可丢的日志/埋点类任务 |
| DiscardOldestPolicy | 丢队列头最老任务 | 追求最新数据、允许丢旧任务 |

> 工程建议：核心业务别用默认 AbortPolicy 直接抛给用户。用 CallerRunsPolicy 或自定义 handler（记录拒绝数 → 告警 → 补偿）。

## 三、参数怎么定（工程口径）

- **CPU 密集**：core ≈ CPU 核数 + 1（少一个避免上下文切换）
- **IO 密集**：core ≈ CPU 核数 × (1 + IO 等待/计算)，常用 2 × 核数
- 公式只是起点，**必须压测 + 监控调参**
- 真正要看的是**瓶颈资源**：CPU？数据库连接池？下游接口 QPS？线程池不是越大越好
- 队列：`LinkedBlockingQueue` 默认无界会内存溢出，必须传容量；要严格控制延迟用 `SynchronousQueue`（不排队直接扩线程）

### 为什么不要用 Executors 快捷方法（阿里规约）

| 快捷方法 | 隐患 |
|---------|------|
| newFixedThreadPool | 无界队列，任务堆积内存溢出 |
| newCachedThreadPool | 最大线程数 Integer.MAX，线程爆炸 |
| newScheduledThreadPool | 无界队列 |
| newSingleThreadExecutor | 无界队列 |

> 一律手动 `new ThreadPoolExecutor` + 自定义 ThreadFactory + 有界队列。

## 四、工程中一般会创建哪几种线程池（按用途分类）

> 核心思想：工程里不是「一个线程池走天下」，而是**按用途分开建**——各池各管各的队列和参数，互不干扰（避免慢任务占满池子、拖死快任务）。每个池都要：业务命名 + 有界队列 + 可监控。

| 种类 | 典型场景 | 参数取向 | 命名习惯 |
|------|---------|---------|---------|
| 通用异步池 | 发短信/邮件/推送、消息通知、日志上报 | core≈核数，max≈2×核数，有界队列，CallerRuns | `biz-async-` / `notify-` |
| 并行批处理池 | 批量导入导出、报表生成、分片查询 | 大队列 + 合理 max，配合 CompletableFuture | `batch-` / `report-` |
| IO 密集调用池 | 调下游 HTTP/gRPC、外部服务 | 线程数可偏大，配合 Semaphore/熔断保护下游 | `rpc-` / `http-` |
| CPU 密集计算池 | 加解密、图像/算法处理 | core≈核数+1，超了反而更慢 | `compute-` |
| 定时任务池 | 定时清理/统计/心跳 | `ScheduledThreadPoolExecutor`；分布式用 xxl-job | `scheduled-` |
| 容器/框架池 | Tomcat 处理 HTTP 请求 | 框架默认（maxThreads=200），业务一般不碰 | Tomcat 自带 |
| 日志异步池 | 日志异步落盘 | logback `AsyncAppender` 自带独立线程 | 框架自带 |

**为什么要分开建（面试能讲透）：**

- **隔离**：批处理大任务占满队列，不会拖死「发短信」这类要响应快的任务
- **各自调参**：IO 密集和 CPU 密集的参数逻辑完全不同，混在一个池没法配
- **各自监控**：哪个池拒绝/积压一眼可查，故障半径小
- 进阶：再按「核心链路 vs 非核心链路」分——核心链路用 CallerRuns 不丢任务，非核心允许丢弃 + 补偿

## 五、实际工程场景（重点）

### 1. 异步化：主流程不阻塞

- 场景：发短信/邮件/推送、日志上报、消息通知、扣库存后的回调
- 主线程提交后立即返回，异步线程慢慢干
- 简单任务用 `execute()`；需要结果用 `submit()` + Future

### 2. 并行分治：大任务拆小任务

- 场景：批量导入导出、报表生成、**多段体检并行分析**（[项目包装-手机性能检测](../FullStack/项目包装-手机性能检测.md)）
- `CompletableFuture.allOf` 聚合子任务结果
- 注意：线程数别超过分片数；每片任务的异常要单独处理，别让一片失败拖垮整体

### 3. 定时/周期任务

- `ScheduledThreadPoolExecutor`：`schedule`（延迟一次）/ `scheduleAtFixedRate`（固定周期）/ `scheduleWithFixedDelay`（上次结束后隔 delay 再跑）
- 不要用 `Timer`：单线程，一个任务异常全部中断
- 分布式多实例：本地定时器每台都执行会重复 → 用 xxl-job / Quartz + 分片 / 分布式锁

### 4. 并发度控制（保护下游）

- 场景：并发调用第三方接口 / 批量写库，防止打爆下游
- 线程池本身限制并发数 + `Semaphore` 双保险
- 与限流（Sentinel / Guava RateLimiter）配合使用

## 六、配套模块知识（扩展）

### 1. JUC 基础

- **BlockingQueue**：`put`/`take` 的阻塞语义是线程池队列的本质（队列空，Worker 阻塞等待）
- **AQS**：线程池的 Worker 用 AQS 实现锁 + 中断状态；ReentrantLock 也基于 AQS
- 锁对比：synchronized（JVM 内置，看 [synchronized.md](Lock/synchronized.md)）vs ReentrantLock（可中断、可超时、可公平）
- 锁粒度要小、避免死锁（关联 [DeadLockDemo.java](DeadLockDemo.java)）

### 2. CompletableFuture（异步编排）

- `runAsync` / `supplyAsync`：**必须传自定义线程池**，默认 ForkJoinPool.commonPool 会被脏任务污染
- 链式：`thenApply` / `thenCompose` / `whenComplete` / `exceptionally`
- 聚合：`allOf`（全部完成）/ `anyOf`（任一完成）
- 异常链：任一节点异常 → 整条链走进 `exceptionally`

### 3. Spring @Async

- 底层就是线程池，`@EnableAsync` 开启
- **必须配自定义线程池**：默认 `SimpleAsyncTaskExecutor` 每任务新建线程，禁止生产使用
- 失效场景：同类自调用（this 调用不经过代理）、非 public 方法
- 异步方法里的事务是独立的，别指望和调用方同事务（关联 [AOP与数据库](../../JavaWeb/06-AOP与数据库.md)）

### 4. Tomcat 容器线程池

- 每个 HTTP 请求占一个 Tomcat Worker 线程（默认 maxThreads=200）
- Controller 里同步做耗时操作 → 占满 Tomcat 线程 → 请求排队超时
- 优化：耗时操作丢业务线程池 / 消息队列异步化，释放 Tomcat 线程
- 高并发 / 超长耗时场景（如 AI Agent 请求）线程池会耗尽 → 演进方向见下（关联 [Servlet与Tomcat](../../JavaWeb/02-Servlet与Tomcat.md)）

### 5. 虚拟线程（Java 21+）与 Goroutine

- IO 密集场景：一个请求一个虚拟线程，阻塞时自动让出内核线程
- 不适用：CPU 密集、重 synchronized 导致 pin 住平台线程
- 存量系统仍是线程池 + 异步化为主，虚拟线程是演进方向
- Go 的 goroutine 是同类思路（关联 [CSP&GMP.md](../../Go/CSP&GMP.md)）

### 6. 监控与优雅停机

- 指标：`activeCount`、`queue.size()`、`completedTaskCount`、**拒绝次数**
- 自定义 ThreadPoolExecutor 覆写 `beforeExecute`/`afterExecute` 打点，或用 Micrometer 暴露
- 动态调参：`setCorePoolSize` / `setMaximumPoolSize`
- 优雅停机：`shutdown()`（不再收新任务）→ `awaitTermination()`（等存量任务）→ 超时 `shutdownNow()`（中断强杀）

## 七、一段能直接用的工程代码

```java
// 线程池配置：手动构造 + 业务名 + 有界队列 + 降级拒绝
@Configuration
public class AsyncConfig {

    @Bean("orderAsyncExecutor")
    public ThreadPoolExecutor orderAsyncExecutor() {
        ThreadFactory factory = new ThreadFactoryBuilder()
                .setNameFormat("order-async-%d")   // 线程名必须业务化
                .build();
        return new ThreadPoolExecutor(
                8,                                // core
                16,                               // max
                60, TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(2000),  // 有界，防堆积
                factory,
                new ThreadPoolExecutor.CallerRunsPolicy()); // 降级不丢
    }
}
```

```java
// 使用：并行分片查询 + 聚合
List<CompletableFuture<List<Order>>> futures = ranges.stream()
        .map(r -> CompletableFuture.supplyAsync(
                () -> orderMapper.queryByRange(r.start, r.end), orderAsyncExecutor))
        .toList();

CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
List<Order> all = futures.stream()
        .flatMap(f -> f.join().stream()).toList();   // 子任务异常在此暴露
```

```java
// 监控：覆写回调打点（也可用 ThreadPoolExecutor 子类）
public class MonitoredExecutor extends ThreadPoolExecutor {
    @Override protected void afterExecute(Runnable r, Throwable t) {
        super.afterExecute(r, t);
        metrics.record("active=" + getActiveCount()
                + " queue=" + getQueue().size()
                + " completed=" + getCompletedTaskCount());
    }
}
```

## 八、面试追问应对速记

| 追问 | 答法要点 |
|------|---------|
| 核心参数有哪些？ | 7 参数 + 提交 4 步流程（先入队后扩线程） |
| 参数怎么设？ | 按 CPU/IO 密集区分 + 压测监控，拒绝拍脑袋 |
| 项目里一般建哪几种线程池？ | 按用途分开建（异步/批处理/IO/定时…），各池隔离、各自调参、各自监控 |
| 拒绝策略怎么选？ | 4 种行为 + 场景：核心用 CallerRuns / 自定义，非核心可丢弃 |
| 队列为什么选它？ | 有界/无界、阻塞语义、SynchronousQueue 不排队 |
| 线程池有哪几种状态？ | RUNNING → SHUTDOWN → STOP → TIDYING → TERMINATED |
| 怎么关闭？ | shutdown + awaitTermination + 超时 shutdownNow |
| 一个任务提交后发生了什么？ | 4 步流程 + Worker 循环从队列 take |
| 线程如何复用？ | Worker 跑完一个任务后 while 循环从 workQueue take 下一个 |
| 为什么不直接用 Executors？ | 无界队列/无界线程的隐患，阿里规约手动构造 |
