# 组件创建、复用与更新的性能瓶颈

> **本质**:组件的耗时集中在三步——**创建**贵在建节点和测量布局，**复用**解决反复创建，**更新**贵在状态变化牵连的组件范围。列表卡顿基本是创建和更新叠加的结果。

## 全景流程

```mermaid
flowchart LR
    A["1 创建<br/>建节点 + 属性 + 测量布局"] --> B["2 复用<br/>滚动时从复用池取, 免重建"] --> C["3 更新<br/>状态变化 → 按依赖精准刷新"]
```

## 1 创建:每个新组件都要过一遍全流程

**干了什么**:实例化 JS 对象、`aboutToAppear`、创建 C++ 节点、设置属性、measure/layout、首帧绘制。列表一次滑入几十个 item，这些全堆在一帧(16.6ms)内。

**瓶颈**:

- **aboutToAppear 里做耗时活**:同步 IO、大 JSON 解析、网络等待都阻塞该组件上屏，拖慢首帧。
- **层级太深**:每层都要 measure/layout，嵌套 5 层以上测量按层数翻倍。
- **用了 Flex**:支持换行和交叉轴对齐，测量要跑两轮；不换行就用 Column/Row。
- **ForEach 全量创建**:List 用 ForEach 一次全建，上万条全上；LazyForEach 只建可见项，`cachedCount` 预载屏外几条。
- **轻内容用了自定义组件**:每个自定义组件都有完整生命周期和状态管理开销；纯展示的重复片段用 @Builder，只是函数调用，不建节点。

## 2 复用:只在滚动场景生效

**干了什么**(@Reusable):item 滑出屏幕不销毁，进复用池；同类组件滑入直接取出，走 `aboutToReuse` 刷新数据，跳过建节点和测量。

**瓶颈**:

- **没开复用**:快速滑动时反复创建销毁节点，创建耗时和 GC 压力全压在滑动路径上。
- **aboutToReuse 里做重活**:复用只省了创建，数据刷新里塞大图解码、深拷贝照样卡。
- **条件不满足等于白标**:@Reusable 必须配合 LazyForEach 才生效，且只在同名组件之间复用。

## 3 更新:状态变化牵连多大范围

**干了什么**:状态变量变化 → 框架沿依赖找到关联组件 → 只重建受影响的分支。牵连范围由你的状态设计决定。

**瓶颈**:

- **@Prop 深拷贝**:@Prop 同步父组件数据时深拷贝一份，大对象、长列表用它拷贝耗时明显；引用类对象改用 @ObjectLink(不拷贝，配合 @Observed)。
- **一个状态绑定一大片**:状态挂在父组件顶层、几十个子组件都依赖，一变全刷。把状态拆小、下沉到最小需要的组件。
- **build 里调函数**:`Text(this.calc())` 每次刷新都重算，高频状态下变成每帧重算。
- **高频事件里改状态**:触摸、滚动回调里直接改 @State，每帧触发一轮依赖刷新；连续变化用 animateTo/属性动画让系统插值，不走状态刷新。
- **@Watch 里再改状态**:回调中又改别的状态，连锁刷新甚至成环。
- **滥用 @StorageLink/@AppStorage**:全局状态，一变牵连所有使用方。

## 速查

| 阶段 | 瓶颈 | 治法 |
| --- | --- | --- |
| 创建 | aboutToAppear 耗时活 | 异步/延迟 |
| 创建 | 层级深、用 Flex | 扁平化，Column/Row 优先 |
| 创建 | ForEach 全量建 | LazyForEach + cachedCount |
| 复用 | 未开复用 | @Reusable + LazyForEach |
| 复用 | aboutToReuse 重活 | 只做数据赋值 |
| 更新 | @Prop 深拷贝 | @ObjectLink |
| 更新 | 状态牵连过宽 | 状态拆小、下沉 |
| 更新 | 高频改状态 | animateTo/属性动画 |

## 一句话总结

创建治"别建那么多"——LazyForEach 加复用；更新治"别刷那么宽"——状态拆小加 @ObjectLink。
