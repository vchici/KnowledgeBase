# 大图对于性能的影响

> **本质**:图大 10 倍，解码、内存、上传、采样全贵 10 倍，显示效果没区别。治法:按显示尺寸解码。

## 五个代价(以 4000×3000 为例)

1. **解码慢**:CPU 解压成像素数组 ≈18ms，一帧才 16.6ms，主线程解码直接掉帧。PNG 是 JPEG 的 2~3 倍。
2. **内存大**:48MB 常驻到回收，占应用内存 18.75%;一屏几张图，连续大块分配可能触发 GC，GC pause 又卡一次主线程。
3. **上传久**：首次绘制要把像素拷给 GPU（[UMA](UMA统一内存.md) 只省了跨总线，拷贝还在），48MB ≈ 3.2ms；纹理缓存放不下，滑一次传一次。
4. **采样废**:View 只要 400×300，GPU 却每帧从 4000×3000 里取色，采样点跳得远，缓存全 miss，每次都从主存读。
5. **列表连锁**:纹理缓存挤爆 → 滑动重传;Bitmap 缓存挤爆 → 回滑重解码。解码 + 上传 + GC 全压在滑动路径上，掉帧连环。

## 治法

让 Bitmap 尺寸 = 显示尺寸。

## 鸿蒙对应:autoResize 与 interpolation

- `autoResize()`:管"解多大"。默认 `true` = 先缩到显示尺寸再渲染，省内存(≈ Android 按尺寸解码);`false` = 按原图解码，内存照原图算。
- `interpolation()`:管"怎么缩"。四档采样算法:`None` 锯齿、`Low` 双线性(默认)、`Medium`、`High`(缩略图最干净，最贵)。

```text
autoResize = true(默认)
压缩文件 ── 解码时就缩到显示尺寸 ──► PixelMap(≈显示大小) ── 每帧 1:1 贴 ──► 屏幕
            ▲ CPU，一次性，插值缩放

autoResize = false
压缩文件 ── 按原尺寸解码 ──► PixelMap(原图大) ── 每帧绘制时缩 ──► 屏幕
                                              ▲ GPU 采样，interpolation 管这步
```

## 为什么控制了尺寸还有缩放

Bitmap 是死的，View 是活的(形状不同、尺寸会变、解码早于测量):重新解码 18ms，GPU 采样几乎免费，框架当然选缩放。绘制本身就是采样，控制 Bitmap 尺寸只是让缩放系数 ≈1、不失真。
