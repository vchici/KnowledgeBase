# Agent 架构 ★

> **本质**：Agent = 以 LLM 为决策大脑的**「感知 → 思考 → 行动 → 观察」循环**，直到达成目标。让 Agent 动起来很容易（一个 while 循环 + 工具），**工程难点是让它稳定收敛**：不跑飞、不死循环、不烧钱、可控可信。

## 核心考点

### 1. Agent vs Chain（一句话分清）

- Chain：**预编排**的固定流程（A→B→C），路径写死。
- Agent：LLM **动态决定**下一步做什么（调哪个工具、要不要继续、何时结束）——用「灵活性」换「确定性」。

### 2. 核心循环（必须能徒手画）

```
目标 → 思考(Reason) → 行动(Act: 调工具) → 观察(Observe: 结果入上下文) → 循环 → 终止(完成/步数上限/需人工)
```

### 3. 经典模式（面试两大件）

- **ReAct**（Reason + Act）：思考轨迹与工具调用交替输出。直觉：模型「边想边做、做完再想」，观察结果修正下一步。**最经典、几乎一切 Agent 框架的底层范式**。
- **Plan-and-Execute**：先让强模型生成任务计划列表，再逐步执行（可换便宜模型），执行中可重规划。适合**长任务**：省 token、全局可控。
- 对比记忆：ReAct 步步为营（灵活但易局部迷失）；Plan-Execute 先谋后动（稳定但计划可能过时）。实际产品常混合。

### 4. 记忆系统（必考分层）

- **短期记忆**：当前上下文窗口内的对话与工具结果。管理手段：裁剪、**滚动摘要压缩**、结构化任务列表（待办式）。
- **长期记忆**：跨会话持久化——**向量库**（语义检索历史，→ [09-Embedding与向量检索](09-Embedding与向量检索.md)）或**结构化存储**（用户画像、事实表）。
- 工程要点：记忆写入要有筛选（不是什么都值得记），读取要按相关度检索注入，而非全量塞入。

### 5. Multi-Agent（面试辨析题）

- 动机：单一上下文塞不下复杂任务的工具+历史；不同角色需要不同系统提示与工具集。
- 编排模式：**中心化**（Supervisor/Planner 分派给 worker，主流可控）vs **去中心化**（Agent 间点对点通信，灵活难调）。
- 常见角色：Planner / Worker / Critic（校对）、Refiner（重写）。
- **清醒认知（高分点）**：Multi-Agent 有额外代价——上下文传递损耗、成本翻倍、调试复杂。**优先用「单 Agent + 好工具 + 好上下文管理」，确有必要再拆多 Agent**（Anthropic 的经验谈）。

### 6. 上下文工程（Agent 第一工程问题）

Agent 运行越久，上下文越爆炸。手段：
- 工具结果**压缩/摘要**后再入上下文（→ [12-FunctionCalling与MCP](12-FunctionCalling与MCP.md)）；
- 历史滚动摘要、旧任务出清；
- **子 Agent 隔离**：派子 Agent 带着任务去跑，只回传结论（上下文不回流全量过程）；
- 外置状态：任务清单/中间产物落文件或 DB，上下文里只留指针。

### 7. 可靠性工程（面试的加分重头）

- **限制**：最大步数、最大 token/成本预算、工具白名单。
- **错误恢复**：工具报错把可读错误回给模型自愈；连续失败 N 次熔断。
- **Human-in-the-loop**：危险/不可逆操作人工确认后再执行。
- **沙箱**：代码执行、文件操作在隔离环境（容器）里跑。
- **全程可观测**：记录每步的思考、调用、结果、成本（trace），否则无法调试。
- **评测**：端到端任务成功率 + 轨迹评估（步骤是否冗余）+ 成本步数指标。

### 8. 框架格局

- **LangGraph**：把 Agent 建模成**图状态机**（节点=步骤，边=流转，状态显式），可控性最好，生产主流。
- OpenAI Agents SDK / Anthropic Claude Agent SDK；AutoGen（微软，对话式多智能体）、CrewAI（角色分工编排）。
- 框架实练：[08-记忆管理策略](../LangChain/08-记忆管理策略/08-记忆管理策略.md)、[06-工具](../LangChain/06-工具/06-工具.md)（LangChain/LangGraph 体系笔记见 LangChain 目录）。

## 面试高频速答

### Agent 跑飞了（死循环/乱花钱）怎么治理？

<details>
<summary>答案</summary>
四层防护：硬限制（步数、预算、超时）→ 状态检查（循环检测：相同工具+相同参数重复出现即熔断）→ 错误可读化让模型自愈 → 危险操作 human-in-the-loop。前提是全链路 trace，否则连「跑飞」都发现不了。
</details>

### 什么时候值得上 Multi-Agent？

<details>
<summary>答案</summary>
三个信号：单上下文确实装不下（工具/历史爆炸）、任务可清晰并行拆分、需要互斥的权限或角色隔离。否则单 Agent + 检索式工具选择 + 上下文压缩更便宜更好调。多 Agent 的通信损耗和成本经常被低估。
</details>
