# 推理优化与部署 ★

> **本质**：LLM 推理的瓶颈 = **显存容量**（装下权重+KV Cache）和**显存带宽**（decode 阶段反复读权重）。所有优化三板斧：**压权重（量化）、管显存（PagedAttention）、凑批次（Continuous Batching）**。

## 核心考点

### 1. 瓶颈分析（一切优化的出发点）

- **Prefill**：一次算整个 prompt，算力密集 → compute-bound，TTFT 的决定因素。
- **Decode**：每 token 都要读全部权重+KV → memory-bound，带宽是天花板。
- 所以：**提升吞吐的核心思路 = 让一次权重读取服务更多 token/请求**（batching、推测解码）。

### 2. 量化（压权重，性价比最高）

- 原理：FP16（2 字节）→ INT8/INT4，用更低位宽存权重。**4bit ≈ 0.5 字节/参数：7B 从 14GB → 3.5GB**。
- 主流算法（都是 PTQ 训练后量化）：
  - **GPTQ**：逐层最小化量化误差，GPU 推理常用。
  - **AWQ**：**激活感知**——少数重要通道（激活大）用高精度保护，其余低精度；掉点更少、对硬件更友好。
  - **GGUF**（llama.cpp 生态）：CPU/端侧推理标准格式，Q4_K_M 等混合精度变体。
- 面试口径：4bit 通常掉 1-2 点以内的通用评测分；**小模型（<3B）对量化敏感**，谨慎。
- 另有 KV Cache 量化（省长上下文显存）。

### 3. FlashAttention（必考）

- 问题：标准注意力要物化 n×n 的中间矩阵，显存 O(n²)。
- 方案：**分块（tiling）+ 在 SRAM 里算完再写出**，从不出 n×n 矩阵；online softmax 技巧保证数值正确。
- 关键认知：**数学上完全等价，不是近似**；省显存 + 减少慢速 HBM 读写（IO-aware），长上下文标配。

### 4. PagedAttention 与 Continuous Batching（vLLM 两大杀器，必考）

- **PagedAttention**：借鉴 OS 虚拟内存分页——KV Cache 切成固定大小的 block 按需分配，不同请求/序列间可共享前缀块。**消灭显存碎片和预留浪费**，同样的卡能塞几倍并发。
- **Static Batching 的问题**：一批请求要等最长的那个做完才能换下一批，GPU 大量空转。
- **Continuous Batching**：**token 级调度**——某请求生成完立即让新请求插入空位，GPU 永远满负荷。吞吐提升 10x+ 级别的关键。

### 5. 推理框架格局（能报出定位即可）

| 框架 | 定位 |
|------|------|
| **vLLM** | 开源通用首选：PagedAttention + Continuous Batching，OpenAI 兼容 API |
| SGLang | 高性能新秀，RadixAttention 前缀复用，结构化生成强 |
| TensorRT-LLM | NVIDIA 官方，单卡极致性能，编译优化，部署门槛高 |
| llama.cpp / Ollama | CPU/端侧，GGUF 量化模型，个人本地跑 |
| DeepSpeed / TGI | 训推一体 / HuggingFace 传统方案 |

### 6. 其他加速手段（名词 + 一句话）

- **推测解码（Speculative Decoding）**：小模型快速起草 k 个 token，大模型一次并行验证，**验证代价 ≈ 一次前向** → 免费提速 2-3 倍，输出分布不变。
- **Prefix Caching**：相同前缀（system prompt、few-shot）的 KV 直接复用 → 多轮对话/固定模板场景 TTFT 大降。
- **Chunked Prefill**：超长 prompt 切块算，避免 prefill 阻塞其他请求的 decode。
- 硬件线：FP8/BF16、多卡张量并行（TP）+ 流水线并行（PP）。

### 7. 服务化工程指标与决策

- 指标：TTFT / TPOT / 吞吐 / P99 延迟 / 单位 token 成本。
- **自建 GPU 推理 vs 云 API**：量大、数据敏感、要定制 → 自建（vLLM）；量小、快速验证、要最新模型 → API。混合：敏感数据本地小模型 + 复杂任务云端大模型。

## 面试高频速答

### vLLM 为什么快？

<details>
<summary>答案</summary>
两大机制：PagedAttention 把 KV Cache 分页管理，消除内部/外部碎片并支持前缀共享，显存利用率翻倍即并发翻倍；Continuous Batching 在 token 粒度动态插入新请求，GPU 不再等整批结束。配合 FlashAttention 与量化，是通用场景默认选择。
</details>

### 量化会掉点吗？AWQ 和 GPTQ 怎么选？

<details>
<summary>答案</summary>
4bit 通常掉 1-2 个点以内，7B+ 模型可接受；小模型掉点明显。GPTQ 逐层最小化重建误差，社区生态最广；AWQ 利用激活分布保护重要通道，精度更稳且对 kernel 更友好。工程上两者都试，用业务评测集说话。
</details>

### 如何提升推理吞吐？

<details>
<summary>答案</summary>
按性价比排序：开 Continuous Batching（vLLM 默认）→ 量化（同卡塞更多并发）→ Prefix Caching（模板场景）→ GQA/KV 量化减 KV → 推测解码。前提是先用 TTFT/TPOT/吞吐定位瓶颈在 prefill 还是 decode。
</details>
