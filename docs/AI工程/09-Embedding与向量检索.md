# Embedding 与向量检索

> **本质**：Embedding 模型把文本映射成高维向量，使**「语义相近 ⇔ 向量距离近」**；向量检索 = 在海量向量里高效找近邻（ANN）。它是 RAG 的地基：召回质量的上限由 Embedding 和索引决定。

## 核心考点

### 1. Embedding 模型

- 来源：BERT 类编码器 + **对比学习**微调（正例拉近、负例推远，用难负例提升区分度）。
- 输出：句向量（通常取 CLS/均值池化），归一化后使用。维度 384 ~ 3072+。
- **选型**（工程必问）：MTEB/C-MTEB 榜单（bge、gte、jina、text-embedding-3 系列）、语言支持、维度（存储成本）、推理成本、是否有 rerank 配套。
- API 现实：SiliconFlow/OpenAI 等 OpenAI 兼容接口居多，注意**模型换版 = 全库重灌**。

### 2. 相似度度量

- **余弦相似度**：比方向不比长度，文本检索主流。
- **内积（IP）**：向量归一化后与余弦等价（所以向量库常只提供 IP）。
- **欧氏距离（L2）**：归一化后与余弦单调等价。
- 记忆点：**先归一化，三种度量基本可以互相转换**，工程默认「归一化 + 内积/余弦」。

### 3. 检索流水线：召回 + 精排（必考两段式）

- **召回（Recall，Bi-Encoder）**：query 离线可比的向量库 ANN 检索，快、可海量，但 query 和文档**各自独立编码**，交互粗糙。
- **精排（Rerank，Cross-Encoder）**：把 (query, doc) **拼接后一起过模型**，逐 token 交互打分——准得多但每对都要算，只能用在 top 几十。
- 结论：**向量召回保底 + rerank 提精**，这是所有生产 RAG 的标配组合。

### 4. ANN 索引算法（面试核心：HNSW）

- **Flat**：暴力全扫，100% 精度，小数据（<10万）直接用。
- **IVF**：先聚类分桶（倒排文件），查询只搜最近的 nprobe 个桶——快但可能漏（桶边界问题）。
- **HNSW（分层可导航小世界图）**：多层跳表式图结构——上层稀疏长边快速定位、下层稠密短边精确逼近；查询从顶层贪心下行。**主流默认**。
  - 参数：`M`（每点连接数，精度/内存）、`ef_construction`（建图质量）、`ef_search`（查询候选队列，**速度↔精度的运行时旋钮**）。
- **PQ（乘积量化）**：向量切段量化压缩，省内存但掉精度，常与 IVF 组合（IVF-PQ，十亿级）。

### 5. 向量数据库格局

| 选型 | 定位 |
|------|------|
| **Chroma** | 轻量嵌入式，原型/中小项目首选 |
| **FAISS** | Meta 的**库**（非服务），自己封装，算法最全 |
| **Milvus** | 分布式生产级，十亿级向量 |
| **pgvector** | Postgres 插件，数据已有 PG 时少一个组件 |
| Qdrant / Weaviate | 云原生，过滤+混合检索特性好 |

- 工程认知：**大多数场景瓶颈不在向量库，在切分和检索策略**。

### 6. 稀疏检索与混合检索（必考）

- **BM25**：词频统计的稀疏检索，**专有名词、型号、代码、罕见词**场景碾压 dense（embedding 对没见过的词不敏感）。
- **混合检索**：dense + sparse 双路召回，**RRF（倒数排名融合）**合并两路排名。
- 现代向量库（Milvus/Qdrant/ES）已内置 sparse 向量与混合检索支持。

## 面试高频速答

### HNSW 原理？

<details>
<summary>答案</summary>
多层近似 Delaunay 图：上层节点稀疏、边「长」，负责跳跃式快速定位；下层稠密、边「短」，负责精细逼近。查询自顶向下贪心走最近邻，复杂度近似 O(logN)。牺牲精确性换速度（ANN），用 ef_search 控制召回率与延迟的平衡。
</details>

### 有了向量检索为什么还要 BM25 / rerank？

<details>
<summary>答案</summary>
dense 向量对专有名词、数字、代码等「字面精确匹配」场景弱（语义平滑把关键差异抹掉了），BM25 补这一路；向量召回是「粗对齐」，top 几十里排序不准，Cross-Encoder 的 rerank 用全交互打分把最相关的顶上去。三件套 = 混合召回 + RRF + rerank。
</details>

### embedding 维度越高越好吗？

<details>
<summary>答案</summary>
不是。维度决定表达上限但增加存储/计算成本，超过模型真实信息量后是浪费且更难索引。选型看 MTEB 实测分与部署成本，而非维度。Matryoshka 表示学习允许一个向量截断成多档维度按需使用。
</details>
