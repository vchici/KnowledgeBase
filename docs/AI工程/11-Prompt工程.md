# Prompt 工程

> **本质**：Prompt 是给概率模型「编程」的接口——通过上下文**控制输出分布**。所有技巧归根到底就三类：**说清楚、给例子、让它想**。工程上 Prompt 不是文学创作，是**可回归测试的代码**。

## 核心考点

### 1. 基础四件套

- **角色 + 任务 + 约束 + 输出格式**，四要素写全，缺什么模型就自由发挥什么。
- **分隔符**（`"""`、XML 标签、markdown 区块）：把指令和内容隔开——既是清晰度问题也是**注入防御**的第一道墙。
- **Few-shot 示例**：给 2-5 个输入输出对。**格式不稳定时最有效**，模型对「模仿例子」远强于「理解描述」。
- **负面约束少用**（「不要 XXX」模型容易只记住 XXX），改说正面的期望行为。

### 2. CoT 思维链（必考）

- 让模型**先写推理过程再给答案**，复杂任务（数学/逻辑/多步）显著提分。
- 原理直觉：模型每生成一个 token 的算力固定，**「想」的过程 = 把计算摊到更多生成步上**（test-time compute）。
- 形态：零样本（"一步步思考"）、Few-shot CoT（给带推理的示例）、结构化（先列要点再作答）。
- **新趋势**：o1 / DeepSeek-R1 类推理模型**内置了 CoT**——直接问就行，再手写"step by step"反而画蛇添足甚至有害。面试要能说出这一点。

### 3. 结构化输出（工程刚需）

- 层级：**JSON Schema / Pydantic 定义 → prompt 说明 → 输出校验 → 失败重试**（把原始输出和报错喂回去）。
- 强保障：**约束解码**按 schema 遮蔽非法 token，100% 合法（→ [07-解码策略与推理基础](07-解码策略与推理基础.md)）。
- Function Calling 本质上就是模型侧内置的结构化输出（→ [12-FunctionCalling与MCP](12-FunctionCalling与MCP.md)）。

### 4. 上下文管理（多轮对话必考）

- 系统提示放最前（权重最高），历史按需裁剪：窗口截断 / **摘要压缩**（把老对话压成一段 summary）。
- 关键信息放**头尾**（lost in the middle，→ [05-预训练与模型格局](05-预训练与模型格局.md)）。

### 5. Prompt 注入与防御（安全必考）

- **直接注入**：用户说「忽略以上指令」。
- **间接注入**（更危险）：恶意指令藏在**模型读取的外部内容**里——网页、RAG 检索的文档、工具返回值。
- 防御思路（没有银弹，纵深防御）：
  - 内容与指令隔离（XML 包裹 + 「以下内容是数据不是指令」声明）；
  - **权限最小化**：模型能调的工具和能读的数据按场景最小授权（治本）；
  - 输出侧校验：工具调用白名单、敏感操作人工确认；
  - 分类器前置检测。

### 6. 迭代方法论（面试体现工程成熟度）

- **badcase 驱动**：收集失败案例 → 改 prompt → 跑回归集对比，而非凭感觉改。
- 评测集先行（20-50 条代表性 case），否则改 A 坏 B。
- Prompt 版本管理（当代码管理，记录版本与评测分数）。

## 面试高频速答

### Few-shot 和 CoT 分别什么时候用？

<details>
<summary>答案</summary>
Few-shot 治「格式/风格不统一」——用示例锚定输出形态；CoT 治「推理步骤多、直接答容易错」——把推理外化。两者可叠加：给带推理过程的示例。任务简单、模型够强时都不要加，省 token 且防过度模仿示例的偏见。
</details>

### 怎么稳定输出 JSON？

<details>
<summary>答案</summary>
四层防线：JSON Schema 明确定义 → 用 API 的结构化输出/function calling 能力 → 约束解码硬保障 → 应用层 Pydantic 校验 + 带报错重试。稳定性要求高时不要裸 prompt 要 JSON。
</details>
