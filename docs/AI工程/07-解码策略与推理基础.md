# 解码策略与推理基础

> **本质**：LLM 生成 = **逐 token 循环执行「前向 → 采样 → 拼接」**。解码策略只回答一个问题：拿到下一个 token 的概率分布后，**怎么从里面挑**。此篇同时建立 KV Cache 与延迟指标的工程直觉——后面推理优化的地基。

## 核心考点

### 1. 两阶段生成（必考：prefill vs decode）

- **Prefill（预填充）**：一次性并行处理整个 prompt，算好每个位置的 KV，产出第一个 token。compute-bound（算力瓶颈）。
- **Decode（解码）**：之后每步只算一个新 token。每步都要读全部权重和 KV Cache → **memory-bound（显存带宽瓶颈）**。
- 这个区分是理解 [08-推理优化与部署](08-推理优化与部署.md) 一切优化的前提。

### 2. 采样策略（参数调优日常）

- **Greedy**：每步取最大概率。确定、稳定，适合代码/抽取，但易重复呆板。
- **Temperature**：logits 除以 T 再 softmax。T<1 分布变尖（保守），T>1 变平（发散）。**控制「敢不敢冒险」**。
- **Top-k**：只在概率前 k 个候选里采样。静态候选集。
- **Top-p（nucleus）**：只在「累计概率达 p 的最小候选集」里采样。**动态候选集**，通常优于 Top-k。
- **重复惩罚 / 频率惩罚**：压重复。长生成必开。
- 常用搭配：对话/创作 `T=0.7~1.0 + top_p=0.9`；抽取/分类/代码 `T=0~0.2`（或直接 greedy）。

### 3. KV Cache（面试必考）

- **问题**：自回归生成第 t 步时，前 t-1 个 token 的 K/V 不变，重算是浪费。
- **方案**：把每层每头的 K/V 缓存下来，每步只算新 token 的 Q/K/V 追加进去。
- **代价**：显存大头。单条序列：`2 × 层数 × KV头数 × head_dim × 序列长 × dtype字节数`。
  - 例：7B（32层, GQA 8头）, FP16, 4K 上下文 ≈ 数百 MB；**并发 × 序列长一长就爆**。
- 压缩线：GQA/MQA 减头数、量化 KV、PagedAttention 管碎片（→ [08](08-推理优化与部署.md)）。

### 4. 显存构成速记

```
总显存 ≈ 权重（参数量×2bytes@FP16） + KV Cache（并发×序列长） + 激活/框架开销
```
7B：权重 14GB；70B：140GB（单卡放不下 → 多卡张量/流水并行或量化）。

### 5. 流式输出与延迟指标（服务化必背）

- **SSE 流式**：token 生成即推送，用户感知大幅提前。
- **TTFT**（Time To First Token）：首 token 延迟，主要由 prefill 决定 → 交互体验关键。
- **TPOT**（Time Per Output Token）：每 token 间隔，由 decode 带宽决定 → 决定「打字速度」。
- **Throughput**：系统整体吞吐（tokens/s），与单请求延迟是**权衡关系**（batch 越大吞吐越高、单请求越慢）。

### 6. Chat Template（工程易错点）

- 多轮对话不是魔法：messages 列表最终被模板拼成**一条 token 序列**（角色标记包裹，系统提示在最前）。
- 自己拼模板时的坑：结尾 assistant 起始标记忘了加、特殊 token 被普通 tokenize、多轮历史截断破坏成对标记。

### 7. 结构化解码（了解）

- 约束解码：按 JSON Schema 构建 token 掩码，非法 token 概率置 0 → **100% 合法 JSON**。vLLM/outlines 支持。比「prompt 里求你别乱来」可靠得多。

## 面试高频速答

### Temperature 和 Top-p 怎么配合？

<details>
<summary>答案</summary>
先 Temperature 定分布形状（保守 vs 发散），再 Top-p 截断尾部噪声。一般二选一调整，另一个留默认；要确定输出时直接 T=0。面试能说出「T 改形状、top-p 改候选范围」即可。
</details>

### KV Cache 为什么省计算、费显存？

<details>
<summary>答案</summary>
省：避免每步对历史 token 重复做 K/V 投影，decode 从 O(t²) 次投影降为每步 1 次。费：缓存本身随 序列长×并发 线性增长，长上下文高并发时超过权重本身，成为显存瓶颈——所以有 GQA、PagedAttention、KV 量化这些优化。
</details>

### 为什么 decode 阶段是显存带宽瓶颈？

<details>
<summary>答案</summary>
每生成一个 token 都要把全部权重和 KV Cache 从显存读一遍，但计算量只有一次前向——算得快、读得慢。所以提升 decode 吞吐的思路是让一次权重读取服务多个请求（batching）。
</details>
