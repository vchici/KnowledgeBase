# 长文档 Token 成本优化

> RAG 的一个缺点是「长文档塞 prompt 有 token 成本」。**说人话**：用户上传了一份 500 页的 PDF，你不可能把它整本塞进模型窗口里——塞不下，塞得下也太贵、模型还会看漏。这篇讲怎么解决。

## 解决思路：别整本塞，只塞有用的，且尽量塞短一点

**① 检索收敛（Retrieval Refinement）：混合检索 + Rerank 收紧 top-k**

靠混合检索 + rerank，把和问题真正相关的几段挑出来，无关的根本不进 prompt。
→ 进来的内容少了，token 自然就省了。这是最基本的一步。

**② 父文档检索（Parent-Document Retrieval）：小块匹配，大块返回**

检索用 300 字的小块（找得准），命中后返回它所在的完整章节（内容全）。
→ 避免了「为了凑齐上下文，胡乱塞一堆大块」的浪费。

**③ 上下文压缩（Context Compression）：LLM 摘要 / LLMLingua**

把检索回来的几段内容，先让 LLM（或压缩工具如 LLMLingua）提炼/删减一遍，只留和问题有关的部分再喂给生成模型。
→ 相当于「先帮模型划重点」。

**④ 分治摘要（Map-Reduce）：分块映射，归并汇总**

文档长到检索也救不了（比如要总结整本书），就切成块分别总结，最后把各段摘要合并起来回答。
→ 不追求一次读完，分批读再拼结论。

**⑤ 长上下文模型（Long-Context LLM）：窗口硬扛**

Gemini、GPT 的长上下文版本能直接吃几十万 token，整本塞进去也行。
→ 最省事但最贵，而且模型对长文中间部分容易「看漏」（lost in the middle），关键信息尽量放开头或结尾。

## 怎么选

一般 RAG 用 ①②③ 就够了；④ 用在「对整份文档做总结」这类场景；⑤ 是懒办法/兜底。

## 一句话

先检索收敛 → 再压缩瘦身 → 实在不行才硬塞长上下文。
