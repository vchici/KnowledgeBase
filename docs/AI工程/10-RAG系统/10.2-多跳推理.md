# 多跳推理

> 针对 RAG 缺点「多跳推理弱」的解释与解法。

## 什么是多跳推理（multi-hop reasoning）

一个问题需要**跨多个文档片段、经过多步跳转才能拼出答案**，单一片段无法直接回答。

**例子**：「A 公司的 CEO 是谁？他毕业于哪所大学？」

1. 先在片段 1 找到「A 公司的 CEO = 张三」；
2. 再根据「张三」去片段 2 找「张三毕业于 XX 大学」。

## 为什么传统 RAG 弱

向量检索是**局部片段匹配**——只会捞和 query 最相似的片段，**天然不会自动串联「片段 1 里的实体」与「片段 2 里关于该实体的信息」之间的关系**。

打个比方：普通检索像在图书馆按关键词找书，一次只能找到书名最像的那几本；但「A 公司 CEO 的母校」这种问题，得先查 A 公司的书写着 CEO 是张三，再拿着「张三」这个名字去查另一本书——检索器自己不会做这第二步。

本质错配：**检索的「单跳」能力 vs 问题的「多跳」结构**。

## 解法一：GraphRAG

**一句话**：不只是存「一段段文字」，还要提前把里面的「实体」和「关系」抽出来，织成一张关系网（知识图谱），检索时顺着网跳。

**怎么做的（离线建图 → 在线查图）**：

```
离线：文档 → LLM 抽取实体（公司/人/产品…）和关系（张三-任职于-A公司）→ 构建知识图谱 → 图谱也向量化
在线：query → 同时检索相关文本片段 + 图谱上的相关实体/子图 → 沿关系边跳转扩展上下文 → LLM 生成
```

- **为什么能解多跳**：问题问「A 公司 CEO 的母校」，图谱里顺着 `A公司 ←任职于— 张三 —毕业于→ XX大学` 两条边就跳完了，不需要「第二次检索恰好用对关键词」。
- **另一个强项**：能回答**全局性/汇总性问题**（「这批文档主要在讲什么主题？」）。普通向量检索只会返回几个最像的片段，永远拼不出全局视角；GraphRAG 可以对图谱做社区聚类、预先生成各主题摘要来回答。
- **代价**：建图要跑大量 LLM 抽取，**离线成本高**；图谱维护也麻烦（文档更新要重新抽取）。适合知识库相对稳定、关系密集的领域（企业内部知识、医疗、法律）。

## 解法二：Agentic RAG

**一句话**：把「检索」从一个固定步骤，变成 Agent 手里可以反复使用的工具——模型自己决定查不查、查什么、查完够不够、要不要再查。

**怎么做的（检索变成循环）**：

```
普通 RAG：query → 检索一次 → 拼答案（一条直线）
Agentic RAG：query → LLM 规划 → 检索 → 判断「信息够吗？」
                ↑                          ↓ 不够
                └──── 带着新线索再检索 ←── 拆子问题/换关键词
                                           ↓ 够了
                                        拼答案
```

- **为什么能解多跳**：回到 CEO 的例子——Agent 第一次查「A 公司 CEO」，从结果里看到「张三」，于是**自动发起第二次检索**「张三 毕业院校」。第一跳的输出变成了第二跳的输入，多跳就是这么一步步走出来的。
- **额外好处**：简单问题可以**跳过检索直答**（省 token）；可以选不同的库/工具查；查到的内容矛盾时还能追加检索交叉验证。
- **代价**：每一轮「判断+规划」都要调 LLM，**延迟和成本比普通 RAG 高几倍**；循环不设上限可能停不下来（要加最大轮数兜底）。适合问题形态多变、无法预先建模关系的场景。

## 怎么选

| 场景 | 选 |
|------|-----|
| 知识库稳定、实体关系密集、常问关系类/全局性问题 | GraphRAG（一次性投入大，查询时又快又准） |
| 问题形态五花八门、不好提前建图、想要灵活 | Agentic RAG（灵活但每一步都烧 token） |
| 两者不互斥：图谱当工具之一，交给 Agent 调度 | 组合用 |
