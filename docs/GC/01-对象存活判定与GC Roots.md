# 如何判断对象可回收

> GC 前必须先回答「谁还活着」：主流 JVM 用**可达性分析**，从一组 GC Roots 出发，能到达的对象是活的，到不了的是"死"的。

## 两种判定算法

### 引用计数法（已弃用）
每个对象维护一个计数器，被引用 +1，解除 -1，为 0 即回收。
- 优点：实现简单、即时。
- 缺点：**无法解决循环引用**（A↔B 互相引用，计数永不为 0）。
- 主流 JVM 未采用。

```java
A a = new A();   // a 计数 1
B b = new B();   // b 计数 1
a.b = b;         // b 计数 2
b.a = a;         // a 计数 2
a = null;        // a 计数 1
b = null;        // b 计数 1
// 两个对象互相引用，计数都不为 0，但已经没用了
// → 引用计数法会误判为"活" → 内存泄漏
```

### 可达性分析（主流）
从 GC Roots 出发，沿引用链向下搜索；**从 GC Roots 不可达的对象，即可回收**。

```mermaid
flowchart LR
    Root["GC Roots"]
    A["可达对象（存活）"]
    B["可达对象（存活）"]
    C["不可达对象（可回收）"]
    Root --> A
    A --> B
    B -.->|"有引用但根不可达"| C
```

## GC Roots 有哪些

可作为根的对象：

| GC Roots | 说明 |
| --- | --- |
| 虚拟机栈（栈帧局部变量表）中引用的对象 | 方法里正在用的对象 |
| 方法区静态属性引用的对象 | `static` 字段指向的对象 |
| 方法区常量引用的对象 | 字符串常量池、`final` 常量 |
| 本地方法栈 JNI 引用的对象 | native 方法引用的对象 |
| 同步锁（synchronized）持有的对象 | 正在被加锁的对象 |
| JVM 内部引用 | 基本类型 Class 对象、异常对象、类加载器等 |

## 一次对象"死亡"的完整流程

1. 可达性分析判定不可达 → **第一次标记**，判断是否需要执行 `finalize()`。
2. 若对象没重写 `finalize()` 或已执行过 → 直接回收。
3. 若需要执行 → 放入 F-Queue，由低优先级线程执行 `finalize()`。
4. 执行期间对象若重新建立与 GC Roots 的连接 → "自救"成功，暂不回收；否则**第二次标记**，回收。

> `finalize()` 已废弃（Java 9 起 `deprecated`），自救机制不可靠，别依赖它。

## 为什么这是内存泄漏的根源

「不可达」才会被回收；**只要存在一条从 GC Roots 到对象的引用链，对象就永远活着**。所谓内存泄漏，本质就是「无用的对象仍被 GC Roots 间接可达」。

- 典型例子：[09-内部类隐式持有外部类引用](09-内部类隐式持有外部类引用.md) 中的 `this$0`，让本该销毁的 Activity 始终可达。
