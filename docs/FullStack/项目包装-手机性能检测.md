# 项目包装：IDE 插件 + 手机性能检测（本地 Trace 分析）

> 目的：把真实做过的项目，在**不编造**的前提下，把"用到的 / 能学到的知识点"显性化、可讲透。
> 铁律：写进简历和面试讲出来的点，必须能扛住深挖 —— 每个点都要想清楚「为什么这么做、怎么做、有什么坑」。

## 一、项目真实背景（准确描述）

- 形态：IDE 插件（本地工具），非云端服务
- 流程：插件连接手机 → 拉起 App 采集性能数据（trace）→ **本地分析** → 结果存**本地数据库**
- 特性：支持**多段体检**（一次体检分多段执行）、**同步分析**、数据持久化

> 注意：数据**不经过云端上报**。一切围绕"本地单机/单服务"展开，包装时不要写成云端架构。

## 二、可包装的技术点清单（逐条可讲）

### 1. 本地数据库设计（真实已有，可深挖）

| 可讲点 | 怎么讲 | 追问应答 |
|--------|--------|---------|
| 建表设计 | 体检记录表、体检段表、分析结果表，一对多关系 | 为什么拆表：多段体检每段独立结果，避免单表过大 |
| 索引 | 结果表按 `device_id + start_time` 建联合索引 | 最左前缀、覆盖索引（关联 FullStack 数据库篇） |
| 事务 | 一段体检的结果写入是原子操作，失败整体回滚 | 隔离级别、什么场景需要事务 |
| SQLite 特性 | 本地库用 WAL 模式提升并发读写 | 读写不互斥，分析线程写、UI 线程读 |
| 冷热归档 | 历史 trace 数据定期归档，控制库体积 | 数据量大时的分层策略 |

### 2. 多段体检 = 任务调度 + 状态机（核心可包装点）

| 可讲点 | 怎么讲 |
|--------|--------|
| 状态机 | 每段体检状态流转：`PENDING → RUNNING → DONE / FAILED / CANCELLED` |
| 状态持久化 | 状态存数据库，插件崩溃重启后能恢复（断点续跑） |
| 段间编排 | 段与段可串行/并行，由状态机驱动，而不是写死顺序 |
| 为什么不用简单 if/else | 段数、顺序、失败重试规则会变，状态机可扩展 |

### 3. 分析任务 = 线程池 / Worker Pool（真实可讲）

| 可讲点 | 怎么讲 |
|--------|--------|
| 并发分析 | 多段体检的分析任务可并行，用线程池（Java）或 goroutine（Go） |
| 控制并发度 | 固定线程数，避免打爆 CPU 和数据库连接 |
| 结果聚合 | 各段分析完成后汇总成总报告 |
| 对比串行 | 同步分析是串行的；包装点：分析异步化 + 结果回调 |

### 4. 本地消息队列（包装点：任务缓冲与解耦）

| 可讲点 | 怎么讲 |
|--------|--------|
| 为什么本地也要队列 | 多台手机同时体检时任务排队，削峰 + 解耦"采集/排队/分析" |
| 落地方式（低成本） | Redis List（`LPUSH` + `BLPOP`）或 Redis Stream；或任务表 + 轮询 |
| 讲队列的通用价值 | 解耦、异步、削峰、失败重试（面试通用话术，配合 FullStack 中间件篇） |
| 不丢任务 | 任务先落库（持久化），再从队列取，处理完更新状态 |

### 5. Redis（包装点：本地缓存 + 队列）

| 可讲点 | 怎么讲 |
|--------|--------|
| 缓存热点结果 | 最近体检报告/重复查询的分析结果走缓存 |
| 缓存三大问题 | 穿透/击穿/雪崩的概念套到本项目怎么防 |
| 缓存一致性 | 结果更新后删缓存 or 更新缓存，延迟双删 |
| 用 Redis 做队列 | 上面第 4 点的实现细节（List/Stream） |

### 6. 幂等与失败重试（包装点：工程严谨性）

| 可讲点 | 怎么讲 |
|--------|--------|
| 幂等 | 同一段体检结果重复写入不产生脏数据：`task_id` 唯一索引 |
| 失败重试 | 分析失败自动重试 N 次，超过进失败列表 |
| 补偿 | 某段失败，整次体检的后续段如何处理（中止 or 跳过） |

### 7. 可观测性（轻量包装点）

- 日志：每段体检的开始/结束/失败打点，异常有堆栈
- 指标：体检次数、成功率、平均耗时、队列积压数
- 排查：任务卡在哪个状态、哪个段，一眼可查

## 三、包装后的一句话描述

> **手机性能检测分析工具**：IDE 插件连接手机拉起 App 采集 trace 数据，本地以**状态机**编排多段体检流程，分析任务经**线程池（Worker Pool）**并行处理、**消息队列**缓冲排队，结果写入**本地数据库**（索引 + 事务 + WAL），并用 **Redis 缓存**热点分析结果；全程**幂等与失败重试**保证任务可靠，Docker 可打包交付。

技术栈标签：
```
Java/Go · SQLite · Redis · 线程池 · 消息队列 · 状态机 · 索引与事务 · 幂等设计 · Docker
```

## 四、面试讲法要点（怎么被追问都不慌）

1. **为什么状态机而不是顺序代码？** —— 段数/顺序/重试规则要可配置、可扩展，状态持久化支持断点恢复
2. **为什么本地也要消息队列？** —— 多设备同时体检时排队削峰；分析与采集解耦；失败可重试
3. **线程池参数怎么定？** —— 分析任务是 CPU 密集（算 trace），核心线程数 ≈ CPU 核数；避免开太多
4. **怎么保证不丢任务/不重复？** —— 任务先持久化再入队；消费后更新状态；`task_id` 幂等去重
5. **Redis 在这里是不是多余？** —— 诚实回答：单机场景缓存收益有限，但可以讲"如果数据量大、查询频繁，Redis 用于缓存与队列是标准做法"

## 五、真实落地最小方案（避免"包装成吹牛"）

| 点 | 最小实现 |
|----|---------|
| 状态机 | 数据库 `status` 字段 + 状态流转校验，够用 |
| 消息队列 | 本地 Redis List（`BLPOP`）或任务表轮询，不用上 Kafka |
| 线程池 | Java `ThreadPoolExecutor` / Go goroutine + `errgroup` |
| 幂等 | 结果表 `task_id` 唯一索引 |
| Redis | 本机跑一个实例，缓存最近分析结果即可 |
| 可观测 | 一个结构化日志 + 简单计数指标 |

> 这 6 项每项都能在一天内真做进项目。**真实做过 > 背话术**，面试官追问时才有东西讲。
