# 项目包装：IDE 插件 + 手机性能检测（本地 Trace 分析）

> 目的：把真实做过的项目，在**不编造**的前提下，把"用到的 / 能学到的知识点"显性化、可讲透。
> 铁律：写进简历和面试讲出来的点，必须能扛住深挖 —— 每个点都要想清楚「为什么这么做、怎么做、有什么坑」。

## 一、项目真实背景（准确描述）

- 形态：IDE 插件（本地工具），非云端服务
- 流程：插件连接手机 → 拉起 App 采集性能数据（trace）→ **本地分析** → 结果存**本地数据库**
- 特性：支持**多段体检**（一次体检分多段执行）、**同步分析**、数据持久化

> 注意：数据**不经过云端上报**。一切围绕"本地单机/单服务"展开，包装时不要写成云端架构。

## 二、技术点清单

### 1. 本地数据库设计

- 三张表：体检记录表、体检段表、分析结果表，一对多（一次体检 → 多段 → 每段多条结果）
- 为什么拆表：每段独立产出结果，避免单表过大、写入互相影响（关系建模与拆表依据见 [字段与表设计](../DataBase/07-字段与表设计.md)）
- 联合索引：结果表按 `device_id + start_time` 建索引，覆盖「按设备 + 时间范围」查询；注意最左前缀（原理见 [数据库索引](../DataBase/02-数据库索引.md)）
- 事务：一段体检的结果写入是原子操作，失败整体回滚（ACID、隔离级别、MVCC 见 [数据库事务](../DataBase/04-数据库事务.md)）
- SQLite 开 WAL 模式：读写不互斥，分析线程写、UI 线程读（锁体系与并发模型见 [锁与并发](../DataBase/05-锁与并发.md)）

### 2. 多段体检编排：状态落库与断点续跑

- 每段体检状态流转：`PENDING → RUNNING → DONE / FAILED / CANCELLED`
- 闪光点：**状态存数据库，插件崩溃重启后从断点续跑**，多段体检不会因退出而半途作废（任务表与恢复流程见 [任务状态与崩溃恢复](../DataBase/08-任务状态与崩溃恢复.md)）
- 实现：`status` 字段 + 流转校验（拒绝非法跳转），段间串行 / 并行按状态驱动
- 说白了就是 if/else + 一张表：「状态机」只是这类写法的通用名字，不是额外技术；值得讲的是落库带来的恢复与可查询能力，不是模式本身

### 3. 分析任务并行化：线程池 / Worker Pool

- 线程分工：调度线程（驱动状态机）产出各段分析任务提交线程池；worker 线程并行解析 trace；UI 线程只读结果，不参与执行
- 并发度：分析是 CPU 密集任务，线程数 ≈ CPU 核数，开多了只增加上下文切换不会更快；配**有界队列**防任务堆积打爆内存（线程池参数与并发原语见 [后端语言与生态](../FullStack/后端/01-后端语言与生态.md)）
- 线程间协作（具体手段）：
  - 等全部完成再聚合：Java 用 `Future` / `CompletableFuture.allOf` 或 `CountDownLatch(段数)`；Go 用 `errgroup` 的 `Wait()`——不是 sleep 轮询
  - 失败快速返回：某段失败后 cancel 其余未开始的任务，不再白等
  - worker 不直接碰 UI：UI 框架是单线程模型，完成后把结果投递回 UI 线程刷新（`invokeLater` / `asyncExec`）；或 UI 直接查库，WAL 下读写不互斥
- 写库收敛：WAL 仍是单写者，多 worker 并发写要么 `busy_timeout` 排队，要么收敛到单写线程批量写（见 [锁与并发](../DataBase/05-锁与并发.md)）
- 闪光点：不在「用了线程池」，在三处细节——①并发度按任务类型算而不是拍脑袋；②用 Future / latch 正确等待聚合，不轮询；③线程边界清晰：分析线程不碰 UI、写库收敛成单点

### 4. 本地消息队列：任务缓冲与解耦

- 作用：多台手机同时体检时任务排队（削峰）；解耦采集、排队、分析三个环节
- 落地：本地消息队列不是独立组件，就是本机 Redis 充当队列，与第 5 点缓存共用同一实例——Redis List（`LPUSH` + `BRPOP`）或 Redis Stream；更轻量用任务表 + 轮询（List 取走即删没 ack、Stream 消费者组 + PEL + XACK 的选型对比见 [消息队列](../DataBase/Redis/消息队列.md)）
- 不丢任务：任务先落库再入队，消费完成后更新状态（实例层 AOF / 入队层先落库 / 消费层幂等，三层链路见 [消息队列](../DataBase/Redis/消息队列.md)）

### 5. Redis：缓存

- 缓存「读多写少」的数据：最近的体检报告、重复查询的分析结果，key 形如 `result:{task_id}`
- 三大问题的对应做法：
  - 穿透（反复查不存在的 task_id）→ 空值缓存：DB 查不到就写短 TTL 的 null，挡住重复空查；恶意随机 key 量大再加布隆过滤器（[缓存穿透](../DataBase/Redis/缓存穿透.md)）
  - 击穿（热点报告 TTL 到期瞬间，大量请求打到 DB）→ 互斥重建：抢到锁的线程查库回填，其余线程稍等重读缓存（[缓存击穿](../DataBase/Redis/缓存击穿.md)）
  - 雪崩（同批写入的缓存同时到期）→ TTL 加随机：`基础时长 + random(0, 5min)`，失效点摊开，DB 不吃尖峰（[缓存雪崩](../DataBase/Redis/缓存雪崩.md)）
- 一致性：先更新数据库、再删缓存；延迟双删兜底——更新后隔一小段时间再删一次，间隔要覆盖一次「读库 + 回填」耗时，读写分离下还要覆盖主从同步延迟（[数据更新](../DataBase/Redis/数据更新.md)）

### 6. 幂等与失败重试

- 幂等：结果表 `task_id` 唯一索引，重复写入不产生脏数据（唯一索引 / 状态机 / 乐观锁等实现对比见 [任务状态与崩溃恢复](../DataBase/08-任务状态与崩溃恢复.md)）
- 失败重试：分析失败自动重试 N 次，超过进失败列表（瞬时 vs 永久失败、退避与重试风暴见同篇）
- 补偿：某段失败后，后续段中止或跳过，需有明确规则（Saga / TCC 见同篇）

### 7. 可观测性

- 日志：每段体检开始 / 结束 / 失败打点，异常带堆栈
- 指标：体检次数、成功率、平均耗时、队列积压数
- 效果：任务卡在哪个状态、哪个段，直接可查

## 三、包装后的一句话描述

> **手机性能检测分析工具**：IDE 插件连接手机拉起 App 采集 trace 数据，本地以**状态机**编排多段体检流程，分析任务经**线程池（Worker Pool）**并行处理、**消息队列**缓冲排队，结果写入**本地数据库**（索引 + 事务 + WAL），并用 **Redis 缓存**热点分析结果；全程**幂等与失败重试**保证任务可靠，Docker 可打包交付。

技术栈标签：
```
Java/Go · SQLite · Redis · 线程池 · 消息队列 · 状态机 · 索引与事务 · 幂等设计 · Docker
```

## 四、讲法要点

1. **状态机不就是 if/else 吗？** —— 是，本质就是 `status` 字段 + 流转校验。价值不在模式名词，在状态落库：崩溃可恢复、进度可查询，这是内存里写 if/else 做不到的
2. **为什么本地也要消息队列？** —— 多设备同时体检时排队削峰；分析与采集解耦；失败可重试
3. **线程池参数怎么定？** —— 分析任务是 CPU 密集（算 trace），核心线程数 ≈ CPU 核数；避免开太多
4. **怎么保证不丢任务/不重复？** —— 任务先持久化再入队；消费后更新状态；`task_id` 幂等去重
5. **Redis 在这里是不是多余？** —— 诚实回答：单机场景缓存收益有限，但可以讲"如果数据量大、查询频繁，Redis 用于缓存与队列是标准做法"

## 五、真实落地最小方案

| 点 | 最小实现 |
|----|---------|
| 状态机 | 数据库 `status` 字段 + 状态流转校验，够用 |
| 消息队列 | 本地 Redis List（`BRPOP`）或任务表轮询，不用上 Kafka |
| 线程池 | Java `ThreadPoolExecutor` / Go goroutine + `errgroup` |
| 幂等 | 结果表 `task_id` 唯一索引 |
| Redis | 本机跑一个实例，缓存最近分析结果即可 |
| 可观测 | 一个结构化日志 + 简单计数指标 |
