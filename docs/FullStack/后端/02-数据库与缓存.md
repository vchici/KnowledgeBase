# 数据库与缓存

> 这一篇只回答一个问题：**数据进系统后，怎么读得快、写得对、改不乱。**
>
> 记住一条演进主线，全文就串起来了——每一步解决上一个问题，又引出下一个：
>
> **存数据（MySQL）→ 快读（索引）→ 并发不乱（事务）→ 还不够快（加 Redis）→ 收拾缓存副作用（一致性 + 锁）**

## 一、MySQL：存得下、找得快

### 索引：让查询从「扫全表」变「走树」

**本质**：磁盘随机读很慢。不加索引查一行要扫全表，加了索引沿着树走，IO 次数从「行数级」降到「树高级」。

- **为什么是 B+ 树**：多叉矮胖，一个 16KB 页能塞几百个键，树高 3~4 层就装下千万行 → IO 次数 = 树高；叶子节点是有序链表 → 天然支持 `BETWEEN`、`>`、`ORDER BY`
- 对比（为什么不选别的）：哈希只能等值查询；红黑树是二叉树、太高；B 树非叶子也存数据、树更高
- **聚簇 vs 非聚簇**：主键索引（聚簇）叶子存整行；二级索引叶子只存主键，查到主键还要回主键索引找整行 → **回表**
- **覆盖索引**：查询的列全在索引里，不用回表，性能最优
- **联合索引**：遵循最左前缀——按定义顺序使用，跳过最左列就失效

### 索引失效：什么情况走不了索引

**本质**：索引是「按列原始值排序」的查找结构。优化器能用它，得同时满足——**条件值 = 索引里的原始值**、**能靠有序性定位**。下面每种都破坏了其中之一：

- 对索引列用函数或计算：`WHERE YEAR(create_time) = 2024` → 索引存「完整时间戳」，条件给「年份」，对不上
- 隐式类型转换：字符串列与数字比较 → 等价于 `CAST(列 AS 数字)`，本质还是「对列做函数」
- 前导模糊：`LIKE '%abc'`（`'abc%'` 不失效）→ `%` 开头起点不确定，有序性用不上
- OR 连接非索引列 → 有一侧必须全表扫，优化器干脆两侧都全表扫
- 联合索引违背最左前缀 → 联合索引按「第一列→第二列」逐层排序，跳过最左列就无序了
- `!=` / `NOT IN` / `IS NOT NULL` → 排除少数值要返回「几乎全部」行，单值定位 + 回表不如直接全表扫

### SQL 优化：让查询走索引、扫得少

1. `EXPLAIN` 看执行计划：`type`、`key`、`rows`、`Extra`
2. 确认走索引，避免全表扫描
3. 只查需要的列，避免 `SELECT *`
4. 大分页：`LIMIT 100000, 20` → `WHERE id > ?` 或游标分页
5. 慢查询日志定位慢 SQL

## 二、MySQL 事务：并发读写不乱

**本质**：单线程没这问题，并发一来，读写互相干扰，于是用事务 + 隔离级别兜住正确性。

三种并发问题，一句话各记住：

- **脏读**：读到别人「没提交」的（可能回滚，读到就错了）
- **不可重复读**：两次读同一行，值变了（别人改了）
- **幻读**：两次读，多出/少了几行（别人插了/删了）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|:----:|:---------:|:----:|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不会 | 可能 | 可能 |
| REPEATABLE READ（MySQL 默认） | 不会 | 不会 | 基本解决 |
| SERIALIZABLE | 不会 | 不会 | 不会 |

InnoDB 在 REPEATABLE READ 下靠两套机制基本解决幻读：

- **快照读**（普通 `SELECT`）→ **MVCC**：事务第一次查询生成 ReadView，全程复用，看不到别的事务新增行（undo log + 版本链 + ReadView）
- **当前读**（`FOR UPDATE` / `UPDATE` / `DELETE`）→ **临键锁** = 行锁 + 间隙锁，锁住已有行及其空隙，阻止插入
- 乐观锁（版本号）vs 悲观锁：并发冲突少的场景用版本号，冲突多的用锁

## 三、Redis：磁盘不够快，加一层内存缓存

**本质**：MySQL 再优化也有磁盘 IO 天花板，于是把 Redis 挡在读请求前面，命中缓存就不碰 DB。

### 三大经典问题：缓存失效时，压力回灌 DB

**记忆点**：穿透 =「查没有的数据」，击穿 =「一个热点过期」，雪崩 =「一片同时过期/宕机」。

| 问题 | 场景 | 解决方案 |
|------|------|---------|
| 穿透 | 查**根本不存在**的数据，缓存 DB 都没有，每次都打库 | 缓存空值（短 TTL）、布隆过滤器、参数校验 |
| 击穿 | **单个热点 key** 过期瞬间，高并发打库 | 互斥锁重建、逻辑过期 |
| 雪崩 | **大量 key 同时过期**或 Redis 宕机 | 过期时间加随机值、多级缓存、限流降级 |

## 四、Redis 进阶：缓存带来的副作用怎么收

**本质**：缓存引入两个新问题——**写的时候数据可能不一致**、**并发抢资源需要互斥**。

### 缓存一致性：先更库、再删缓存

**主流方案（Cache Aside + 删缓存，不是更新缓存）**：

1. 写：先**更新数据库**，再**删除缓存**（更新缓存会并发覆盖，且写多读少时白写）
2. 读：缓存未命中 → 查库 → 回填

**并发缝隙与兜底**：

- 极端时序（读旧库 + 写新库 + 回填旧值）概率低，用**延迟双删**：写完删一次，延迟几百 ms 再删一次
- 删缓存失败 → **消息队列重试**，或 **Canal 订阅 binlog → MQ → 消费者删缓存**（binlog 是事实源，Canal 不 ack 不推位点，MQ 持久化重试，DEL 幂等）
- 最后防线：缓存设**过期时间**，不一致窗口有上界

**结论**：强一致要分布式锁串行化读写，代价太高；实际普遍接受**最终一致**——「先更库后删缓存 + 延迟双删 + binlog 兜底 + TTL」是标准组合。

### 分布式锁：并发互斥 + 防误删

```python
# Redis 分布式锁（SET NX EX + Lua 释放）
import redis
r = redis.Redis()

# 加锁：一条命令原子完成「不存在才设置 + 带过期时间」
ok = r.set('lock:order', 'unique-id', nx=True, ex=10)

# 释放：Lua 保证「判断持有者 + 删除」原子，防止误删别人的锁
lua = """
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
"""
r.eval(lua, 1, 'lock:order', 'unique-id')
```

**防误删的完整链路**：

1. value 写入唯一标识（UUID + 线程 ID），释放前比对，不是自己的不删
2. 「比对 + 删除」必须 Lua 原子，否则中间锁可能过期易主
3. 业务耗时不可预估时，用**看门狗自动续期**（Redisson watchdog），而不是盲目加大 TTL

## 常见面试题

> 点击展开参考答案，先自测再看。

### 1. 索引为什么用 B+ 树而不用红黑树/哈希？

<details><summary>参考答案</summary>

| 对比对象 | 缺陷 | B+ 树的优势 |
|---------|------|------------|
| 哈希索引 | 只能等值查询，不支持范围查询和排序 | 叶子节点有序链表，天然支持 `BETWEEN`、`>`、`ORDER BY` |
| 红黑树/AVL | 二叉树，千万数据树高达 20+ 层，每层一次磁盘 IO | 多叉矮胖：一个 16KB 页放上百个键，3~4 层撑起千万级数据，IO 次数 = 树高 |
| B 树 | 非叶子节点也存数据，单页能放的键更少，树更高 | 非叶子节点只存键，树更矮；叶子链表利于范围扫描 |

核心逻辑：磁盘 IO 是按页读的，**树的高度决定 IO 次数**，B+ 树把树压到最矮、又保住了范围查询能力。

</details>

### 2. 什么情况下索引会失效？

<details><summary>参考答案</summary>

- 对索引列使用**函数或计算**：`WHERE YEAR(create_time) = 2024`
- **隐式类型转换**：字符串列与数字比较（`phone = 13800000000`）
- **前导模糊查询**：`LIKE '%abc'`（`'abc%'` 不失效）
- **OR 连接非索引列**：任一侧无索引则全表扫描
- **联合索引未遵循最左前缀**：跳过第一列直接查后面的列
- 补充：`!=` / `NOT IN` / `IS NOT NULL` 不一定走索引，优化器会基于成本估算决定（回表代价太高时宁可全表扫）

排查手段：`EXPLAIN` 看 `type`（ALL 为全表扫）、`key`（实际用到的索引）、`rows`（预估扫描行数）。

</details>

### 3. MySQL 默认隔离级别？如何解决幻读？

<details><summary>参考答案</summary>

默认 **REPEATABLE READ**（可重复读）。InnoDB 在该级别通过两套机制基本解决幻读：

- **快照读**（普通 `SELECT`）：**MVCC**——事务第一次查询时生成 ReadView，整个事务期间复用，看不到其他事务新增的行
- **当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）：**临键锁（Next-Key Lock）** = 记录锁 + 间隙锁，锁住已有记录及其间的空隙，阻止其他事务插入

注意边界：事务内**先快照读后当前读混用**时，仍可能读到幻影行（MVCC 快照挡不住当前读），所以说"基本解决"而非"彻底解决"。

</details>

### 4. 缓存穿透/击穿/雪崩的区别与解决方案？

<details><summary>参考答案</summary>

| 问题 | 触发场景 | 解决方案 |
|------|---------|---------|
| **穿透** | 查询**根本不存在**的数据，缓存和 DB 都没有，每次都打库 | 缓存空值（短 TTL）；布隆过滤器前置拦截；入口参数校验 |
| **击穿** | **单个热点 key** 过期瞬间，高并发同时打库 | 互斥锁重建（只放一个线程回源）；逻辑过期（物理上永不过期 + 异步刷新） |
| **雪崩** | **大批 key 同时过期**，或 Redis 整体宕机 | 过期时间加随机值打散；多级缓存；限流降级；Redis 高可用（哨兵/集群） |

一句话区分：穿透是"查没有的数据"，击穿是"一个热点过期"，雪崩是"一片同时过期/宕机"。

</details>

### 5. Redis 分布式锁的实现？如何避免锁误删？

<details><summary>参考答案</summary>

**基础实现**（见上文代码）：

- 加锁：`SET lock:order unique-id NX EX 10`，一条命令原子完成"不存在才设置 + 带过期时间"
- 释放：Lua 脚本原子执行"校验持有者 + 删除"

**误删场景**：线程 A 执行超时，锁过期后被 B 抢到；A 执行完毕直接 `DEL`，删掉的是 B 的锁，此时 C 又能加锁——锁互斥被破坏。

**避免方案**：

1. value 写入**唯一标识**（UUID + 线程 ID），释放前先 `GET` 比对，不是自己的就不删
2. "比对 + 删除"必须用 **Lua 保证原子性**，否则 GET 和 DEL 之间锁可能恰好过期易主
3. 进阶：业务执行时间不可预估时，用**看门狗自动续期**（Redisson 的 watchdog），而不是盲目加大 TTL

</details>

### 6. 如何保证数据库与缓存的一致性？

<details><summary>参考答案</summary>

**主流方案：Cache Aside + 删除缓存**

1. 写：先**更新数据库**，再**删除缓存**（不是更新缓存——并发写会互相覆盖，且写多读少时白写）
2. 读：缓存未命中 → 查库 → 回填缓存

**并发缝隙与兜底**：

- 极端时序（读旧库 + 写新库 + 回填旧值）概率低，用**延迟双删**：写完删一次，延迟几百 ms 再删一次，清掉并发期间回填的旧值
- 删除缓存失败 → **消息队列重试**，或 **Canal 订阅 binlog → MQ → 消费者删缓存**，实现最终一致性（binlog 是变更事实源，Canal 不 ack 不推进位点，MQ 持久化 + 重试，DEL 幂等）
- 最终兜底：缓存设置**过期时间**，不一致窗口有上界

**结论**：强一致要靠分布式锁把读写串行化，代价太高；实际系统普遍接受**最终一致**——"先更库后删缓存 + 延迟双删 + binlog 订阅兜底 + TTL"是标准组合。

</details>
