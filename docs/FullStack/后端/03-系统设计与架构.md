# 系统设计与架构

> 这一篇回答「一个请求从进来到返回，系统怎么做到**接得住、认得出、扛得住、改不乱**」。
>
> 记忆主线（跟着一次请求走）：
>
> **API 怎么对接 → 怎么证明你是谁（认证）→ 人多了怎么扛（高并发）→ 多服务怎么协同（分布式）→ 综合怎么设计（经典题）**

## 一、API 设计：请求怎么进、怎么回

**本质**：对外接口是系统的门面，约定越清晰，越不容易被误用、越容易排错。

### RESTful 规范

| 原则 | 说明 | 示例 |
|------|------|------|
| 资源用名词 | URL 表示资源，不用动词 | `GET /users`，而不是 `/getUsers` |
| HTTP 方法表达动作 | GET/POST/PUT/DELETE | |
| 状态码语义化 | 2xx 成功 / 4xx 客户端错误 / 5xx 服务端错误 | 404 资源不存在、429 限流 |
| 版本管理 | URL 前缀或请求头 | `/api/v1/users` |

### 统一响应与错误处理

```json
// 统一响应结构
{
  "code": 0,           // 0 成功，非 0 业务错误码
  "message": "ok",
  "data": { }
}
```

- 全局异常处理：拦截器捕获后转成统一结构
- 参数校验：前端校验 + 后端校验都要做（安全边界）
- 幂等设计：`Idempotency-Key` 请求头 / 唯一业务号 + 防重表

## 二、认证与授权：证明「你是谁、你能干什么」

**本质**：HTTP 无状态，每次请求都得带身份凭证，区别只在**凭证存哪、怎么校验**。

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| Session | 服务端存会话，客户端存 cookie | 简单，但分布式需共享存储（Redis 存 session） |
| JWT | 无状态 Token，签名自校验 | 天然支持分布式，但难以主动失效、Token 变大 |
| OAuth2 | 第三方授权（授权码模式） | 接入微信/Google 登录 |
| SSO | 统一登录，多个系统共享认证 | 企业内部系统常用 |

- JWT 结构：Header.Payload.Signature
- 常见安全问题：Token 泄露、签名算法（alg=none 攻击）、过期时间设置
- 刷新令牌（refresh token）：短期 access token + 长期 refresh token

## 三、高并发应对：人多了，把压力分层消化

**本质**：扛并发不是硬顶，而是**逐层挡**——能挡在 CDN/缓存/队列的，就不让它打到数据库。

### 分层策略

```
客户端 → CDN → 网关(限流/鉴权) → 应用服务(无状态,可水平扩展)
             ↓
          缓存层(Redis,抗读流量)
             ↓
          消息队列(削峰填谷,异步解耦)
             ↓
          数据库(主从/分库分表)
```

### 核心手段

| 手段 | 解决什么 | 要点 |
|------|---------|------|
| 水平扩展 | 容量不足 | 服务无状态化，负载均衡 |
| 缓存 | 读压力 | 缓存三大问题防护（见数据库文档） |
| 消息队列 | 流量峰值、解耦 | Kafka/RabbitMQ，消费幂等 |
| 限流 | 保护下游 | 计数器/滑动窗口/令牌桶/漏桶 |
| 降级熔断 | 依赖故障 | 熔断器（Hystrix/Sentinel）、超时控制 |
| 异步化 | 响应时间 | 异步任务、事件驱动 |
| 数据库优化 | 慢查询 | 索引、分库分表、读写分离 |

## 四、分布式核心难题：拆成多服务后，一致性怎么保证

**本质**：单机没有这些问题。服务一拆，网络不可靠、数据分散，就冒出了**分布式事务、幂等、全局 ID**。

### 分布式事务

| 方案 | 思路 | 适用 |
|------|------|------|
| 2PC | 两阶段提交（准备+提交） | 强一致，性能差 |
| TCC | Try-Confirm-Cancel 补偿 | 金融级强一致 |
| Saga | 长事务拆子事务+补偿 | 订单流程 |
| 本地消息表 / 事务消息 | 最终一致 + MQ | 通用业务，最常用 |

### 幂等性

- 为什么需要：网络重试、MQ 重复投递、用户重复点击
- 方案：唯一业务号 + 唯一索引、状态机校验、Token 机制

### 分布式 ID

- UUID（不递增）、雪花算法（Snowflake，时间戳+机器号+序列号）、Redis 自增、号段模式

## 五、经典设计题：综合运用前面的能力

**本质**：设计题不是背答案，是看你会不会把「限流/缓存/队列/锁/幂等」按场景组合。

| 题目 | 关键考察点 |
|------|-----------|
| 设计短链系统 | 发号器、跳转 302、缓存热点 |
| 设计秒杀系统 | 限流、缓存库存、MQ 削峰、防超卖 |
| 设计消息队列 | 存储、ACK、顺序性、可靠性 |
| 设计抢红包 | 预分配、拆红包算法、并发控制 |
| 设计排行榜 | Redis ZSet |
| 设计分布式锁 | 见数据库文档 |

## 常见面试题

> 点击展开参考答案，先自测再看。

### 1. JWT 与 Session 的区别？各自适用场景？

<details><summary>参考答案</summary>

| 维度 | Session | JWT |
|------|---------|-----|
| 存储 | 服务端存会话，客户端只存 cookie | 客户端存 Token，服务端无状态 |
| 分布式 | 需共享存储（Redis） | 天然支持，服务端不用存 |
| 主动失效 | 容易（删 session） | 难（只能等过期或黑名单） |
| 体积 | 小 | 大（携带 payload） |

**场景**：单体或内部系统用 Session 简单可控；微服务/跨域/前后端分离用 JWT。

</details>

### 2. 如何设计一个限流系统？（令牌桶实现）

<details><summary>参考答案</summary>

**令牌桶**：固定速率往桶里放令牌，请求先取令牌，取到才放行，桶满则丢弃令牌（允许一定突发）。

- 实现：Redis + Lua 原子操作（记录上次补充时间 + 当前令牌数），保证分布式下计数准确
- 对比：计数器（简单但临界突变）、滑动窗口（平滑但占内存）、漏桶（匀速但无法突发）、令牌桶（允许突发，最常用）

</details>

### 3. 分布式事务有哪些方案？你们项目怎么做的？

<details><summary>参考答案</summary>

- **2PC**：准备+提交两阶段，强一致但性能差、存在协调者单点
- **TCC**：Try-Confirm-Cancel，业务自己实现补偿，金融级强一致
- **Saga**：长事务拆子事务+补偿，适合订单流
- **本地消息表 / 事务消息**：本地事务和发消息原子化，MQ 异步推进，**最终一致**，通用业务最常用

项目落地一般选**本地消息表 + MQ 最终一致**：先落业务数据 + 消息表（同一事务），再异步发 MQ，消费端幂等，配合对账兜底。

</details>

### 4. 如何保证接口幂等？

<details><summary>参考答案</summary>

- **唯一业务号 + 唯一索引**：提交时带业务号，DB 唯一索引挡重复（最通用）
- **状态机校验**：状态流转只允许单方向，重复请求命中非法状态直接拒绝
- **Token 机制**：先取 token，提交时校验并删除 token，第二次提交无 token 直接拦截
- **乐观锁版本号**：更新带版本，重复更新影响行数为 0

</details>

### 5. 秒杀系统的架构如何设计？如何防超卖？

<details><summary>参考答案</summary>

**架构分层**：

1. **限流**：网关层令牌桶，挡掉大部分流量
2. **缓存库存**：Redis 预扣（Lua 原子 DECR），判断是否有库存，不用先打 DB
3. **MQ 削峰**：抢到资格的用户进队列，异步下单，保护 DB
4. **防超卖**：Redis Lua 原子预扣（`库存 < 0 拒绝`）+ DB 唯一索引（用户+商品）最终兜底
5. **数据一致性**：下单成功后异步减真实库存，配合对账

</details>
