# 后端语言与生态

> 这一篇回答「后端学什么语言、语言之外还要会什么」。
>
> 记忆主线：**选对工具（选型）→ 用好工具（语言核心）→ 跳出工具看不变能力（通用基本功）**。
>
> 底层信念：语言只是工具，真正值钱的是网络、数据库、并发、架构这些**不随语言变**的知识。

## 一、主流选型：按场景选工具，别迷信某门语言

| 语言 | 框架 | 特点 | 适合 |
|------|------|------|------|
| Java | Spring Boot | 生态最全、稳定、企业级 | 大型业务系统、银行/电商 |
| Go | Gin / Kratos | 高并发、单二进制易部署、性能好 | 中间件、微服务、云原生 |
| Node.js | Express / NestJS | 前后端同语言、I/O 密集 | BFF 层、快速原型 |
| Python | FastAPI / Django | AI 生态强、开发快 | AI 服务、数据平台 |
| Rust | Axum / Actix | 极致性能与安全 | 基础设施、高性能服务 |

> 建议：**精通一门（Java 或 Go），理解其他**。语言会过时，网络/数据库/并发/架构不会。

## 二、语言核心：学透一门语言的「内存 / 并发 / 框架」三件套

**本质**：任何语言都能拆成三块底层——**内存怎么管、并发怎么写、框架怎么搭**，学透一门即可迁移到其他语言。

### Java

- **内存**：JVM 内存模型（堆/栈/方法区）、GC 机制（分代回收、G1/ZGC）
- **并发**：synchronized / ReentrantLock / AQS / 线程池 / volatile / CAS
  - 关联笔记：[synchronized 详解](../../Thread/Lock/synchronized.md)
- **集合（含并发容器）**：ArrayList vs LinkedList、HashMap 原理（数组+链表+红黑树）、ConcurrentHashMap（分段锁/CAS）
- **框架**：Spring 生态——IoC/DI、AOP、Bean 生命周期、事务传播
  - 关联笔记：[IoC-DI](../../JavaWeb/04-IoC-DI.md)、[AOP与数据库](../../JavaWeb/06-AOP与数据库.md)
- **工程化**：异常体系与日志（SLF4J + Logback）

### Go

- **并发**：goroutine 与 channel——GMP 调度模型、CSP 并发模型
  - 关联笔记：[Goroutine/GMP](../../Go/CSP&GMP.md)
- **语言特性**：指针与值传递、接口（鸭子类型）、错误处理（error 值 vs panic）
- **标准库**：net/http、context、sync 包
- **微服务框架**：Kratos / Go-zero，rpc（gRPC）

## 三、通用能力：换任何语言都逃不掉的后端基本功

**本质**：语言是表层，下面这些是后端通用的「骨架」，语言换了它们还在。

1. **HTTP 服务编程**：路由、中间件、请求上下文、状态码语义
2. **Web 框架原理**：Servlet/Filter/拦截器、AOP 适用场景
3. **多线程与异步**：线程池参数设计、异步任务、消息驱动
4. **数据访问**：ORM 用法与原生 SQL 的平衡、事务管理
5. **参数校验与错误处理**：统一响应结构、全局异常、校验注解/中间件
6. **测试**：JUnit/Go test、Mock、Testcontainers

### 1. HashMap 底层原理？ConcurrentHashMap 如何保证线程安全？

<details><summary>参考答案</summary>

**HashMap**：数组 + 链表 + 红黑树，三者各司其职：

- **数组（桶）**：哈希表主体，`key.hashCode()` 取模定位到某个下标，O(1) 找到桶
- **链表**：不同 key 哈希冲突落在同一桶时，挂在数组元素后面，解决冲突
- **红黑树**：桶内链表太长时查找退化成 O(n)，超过阈值转红黑树，找回 O(log n)

配合逻辑：数组负责「快速定位桶」→ 冲突了挂链表 → 链表太长转红黑树兜底。树化有两个条件：**链表长度 > 8 且数组长度 ≥ 64**——数组太小时优先扩容而不是急着树化（此时哈希分布不均，扩容更划算）。扩容（负载因子 0.75 = 元素个数 / 桶数组长度）时重哈希，JDK 8 用高低位拆分减少迁移。

**ConcurrentHashMap**：JDK 8 放弃分段锁，写操作按「桶的状态」分工。

先理解 CAS（Compare And Swap，比较并交换）：一条 CPU 硬件原子指令——「目标位置**还是**我以为的旧值吗？是 → 换成新值；不是 → 失败」。一条指令完成，中间不可能被别的线程插队，所以不用加锁也能保证原子。CAS只能包住「一次比较+一次写入」，没有办法包住遍历的多步循环；「读尾巴」和「写 next」永远是分离的两步，中间就有空隙，此时就需要synchronized锁头节点。

- **空桶 → CAS**：put 即「桶还是 null，才放进去」，一次原子写入完成插入。两线程抢同一空桶：一个成功，另一个失败后重走流程（发现桶非空 → 转下面的加锁分支），没有谁阻塞谁。哈希分散时空桶是常态，所以大多数写操作全程无锁
- **非空桶 → synchronized 锁头节点**：链表尾插是「遍历到尾 + 修改 next」复合操作，CAS 只能保证单次赋值，保不住多步原子性，必须互斥。但只锁当前桶的头节点，别的桶不受影响
- **锁内 double-check**：拿到锁后再核对一次头节点没变（防止「判断非空」到「锁到手」之间被并发树化/迁移改动）
- **读全程无锁**：Node 的 val/next 用 volatile 保证可见性

并发度从 JDK 7 的「段数（默认 16）」提升到「桶数」。

</details>

### 2. 线程池核心参数如何设置？

<details><summary>参考答案</summary>

核心参数：核心线程数、最大线程数、队列、拒绝策略、存活时间。以 8 核机器（N=8）举例：

- **线程数——看线程在「算」还是在「等」**：
  - 上下文切换发生时机：
    - 时间片用完（OS强制轮换）
    - 线程阻塞（等锁、等IO、sleep）
    - 高优先级线程就绪（抢占）
  - CPU 密集（图片压缩/转码，线程从不等待）→ `N+1 = 9`：核就 8 个，线程再多只会徒增上下文切换（一个核同一瞬间只能执行一个线程的指令，切换就是把当前线程的上下文保存起来，切换到下一个线程的上下文执行）；CPU密集时，切换会少，`+1` 是防偶发暂停时核不闲着。
  - IO 密集（调下游 HTTP / 查库，时间都花在等响应）→ `2N = 16`：一部分线程在等时，另一些在算，把等待时间填满
  - 等待/计算比例极端时用公式 `N * (1 + 等待/计算)`：任务 = 查库 90ms（等）+ 计算 10ms（算）→ `8 * (1+9) = 72`。只是起点，最终靠压测校准
- **队列——大促流量突增 10 倍时见分晓**（QPS = Queries Per Second，每秒请求数，如从 100 QPS 涨到 1000）：
  - 无界队列（`newFixedThreadPool` 内置的 `LinkedBlockingQueue`）：任务入队远快于消费，队列无限涨 → OOM，整个服务挂
  - 有界队列（`ArrayBlockingQueue`，容量 1000）：满了立刻走拒绝策略，压力显式化，内存有上界
- **拒绝策略——挤爆了丢谁，看任务性质**：

| 策略 | 场景 | 效果 |
|------|------|------|
| AbortPolicy（默认） | 用户下单接口 | 抛异常 → 返回「系统繁忙请重试」，用户感知 |
| CallerRunsPolicy | 日志入库等**不能丢**的内部任务 | 提交线程自己执行，没空接新请求 → 上游自动减速（天然背压） |
| Discard / DiscardOldest | 埋点上报、监控采样 | 静默丢弃 / 丢最老的，保命要紧 |

串起来记：线程数决定「同时干多少」，队列决定「挤不挤」，拒绝策略决定「挤爆了丢谁」。

</details>

### 3. Spring Bean 的生命周期？

<details><summary>参考答案</summary>

实例化 → 属性注入 → `BeanNameAware`/`BeanFactoryAware` 回调 → `BeanPostProcessor` 前置处理 → `@PostConstruct` → `InitializingBean` → `BeanPostProcessor` 后置处理（**AOP 代理在此生成**）→ 使用 → `@PreDestroy` 销毁。

**了解它的意义——不是背顺序，是能回答三类实际问题**：

1. **代码能插在哪（扩展点）**：Aware 回调、`BeanPostProcessor` 前置/后置、`@PostConstruct`、`InitializingBean` 全是 Spring 留的钩子，想在初始化前后做点事（校验配置、注册回调、埋点）从这里选位置；中间件/starter 源码几乎全靠 `BeanPostProcessor` 挂进 Spring（`@Autowired` 本身就是 `AutowiredAnnotationBeanPostProcessor` 处理的）
2. **为什么顺序是这样（时序坑）**：属性注入排在初始化之前，所以 `@PostConstruct` 里能安全用 `@Autowired` 字段；构造器里注入还没发生，用注入字段直接 NPE
3. **代理什么时候诞生（AOP/事务失效的根）**：代理在后置处理阶段才生成——类内部 `this.method()` 调用的是原始对象、绕过了代理，`@Transactional`/切面失效

面试重点：AOP 代理在后置阶段生成，所以同类自调用 `this.method()` 绕过了代理，事务/切面不生效。

</details>

### 4. Spring 事务什么时候会失效？

<details><summary>参考答案</summary>

先理清两个概念，失效场景才好懂：

**事务（数据库层面）**：一组 SQL 作为一个**不可分割的整体**——要么全部成功（commit），要么全部失败回滚（rollback），回到执行前的状态。经典例子：转账 = A 扣 100 + B 加 100，必须同时成功，只成功一半钱就凭空消失。四个特性（ACID）：原子性（不可分割）、一致性（前后都是合法状态）、隔离性（并发事务互不干扰）、持久性（提交即永久）。

**Spring 事务**：数据库本身就有事务能力，Spring 做的是把「开事务、提交、回滚」从业务代码里抽走——方法加 `@Transactional` 后，AOP 代理在方法执行**前**开事务（`setAutoCommit(false)`），正常返回就 commit，抛出异常就 rollback。

**由此 `@Transactional` 生效有三个前提**：① 调用必须经过代理 ② 异常必须抛到代理这一层 ③ 异常类型在回滚规则内。下面的失效场景，全是破坏了某个前提：

- **自调用**：同类内 `this.method()` 走的是原始对象不是代理，破坏前提①
- **异常被吞**：try-catch 吃掉异常，没抛到代理层，破坏前提②
- **受检异常默认不回滚**：默认只回滚 RuntimeException/Error（非受检），受检异常需 `rollbackFor` 指定，破坏前提③
- **方法非 public**：代理无法拦截，破坏前提①
- **传播属性错误**：如 `NOT_SUPPORTED` 挂起事务
- 数据库引擎不支持事务（MyISAM）：底层没有事务能力，代理白搭

</details>

### 5. goroutine 与线程的区别？GMP 调度模型？

<details><summary>参考答案</summary>

| 维度 | goroutine | 线程 |
|------|----------|------|
| 栈大小 | 初始 2KB，可动态伸缩 | 默认 1MB，固定 |
| 切换 | 用户态，成本低 | 内核态，成本高 |
| 数量 | 可轻松百万级 | 受内存和调度限制 |

**GMP**：G（goroutine）、M（内核线程）、P（逻辑处理器，持有本地 runq）。P 数量 = `GOMAXPROCS`；M 从 P 的本地队列取 G 执行，本地空则 work-stealing 偷别的 P 的 G。G 阻塞时 M 让出，P 找新 M 继续跑——实现「用户态调度 + 复用内核线程」。

</details>

### 6. JVM 内存泄漏如何排查？

<details><summary>参考答案</summary>

- 现象：老年代持续增长、Full GC 后内存仍不降、最终 OOM
- 工具：`jps` 找 pid → `jmap -dump` 导出堆 → MAT/VisualVM 分析；`jstat -gcutil` 看各代占用趋势
- 定位：从 GC Roots 找对象引用链，看谁被长期持有（静态集合、ThreadLocal 未 remove、未关闭的流/连接）
- 关联笔记：[内存泄漏](../../GC/内存泄漏.md)

</details>
