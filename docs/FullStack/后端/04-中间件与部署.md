# 中间件与部署

> 这一篇回答「业务代码写完之后，靠什么扛流量、怎么把它交付上线、上线后怎么看护」。
>
> 记忆主线（开发到运维的完整链路）：
>
> **靠中间件扛流量（MQ/ES）→ 打包成镜像（Docker）→ 部署上线（Linux/Nginx/CI-CD）→ 上线后看护（可观测）→ 云原生演进**

## 一、消息队列：异步解耦、削峰填谷

**本质**：让「生产」和「消费」解耦，用队列当缓冲——流量峰值先入队，下游按自身能力消费。

### 应用场景

1. **异步解耦**：订单创建后发消息，后续服务异步消费
2. **削峰填谷**：秒杀流量先入队，下游按自身能力消费
3. **最终一致**：跨服务数据同步，配合本地消息表

### 核心概念

| 概念 | 说明 |
|------|------|
| Producer / Consumer | 生产者 / 消费者 |
| Broker | 消息服务器 |
| Topic / Partition | 主题 / 分区（并行度与顺序性的权衡） |
| Offset | 消费者消费位置 |
| ACK | 消费确认机制（手动 ack 保证不丢） |

### 可靠性三问：不丢、不重、不乱序

| 问题 | 方案 |
|------|------|
| 消息不丢 | 生产端 ack 确认 + 分区副本（replica）+ 消费端手动 ack |
| 消息不重复 | 消费幂等（唯一业务号 + 去重表） |
| 消息有序 | 单分区单消费者，或按业务 key 路由到固定分区 |

### RabbitMQ vs Kafka

| | RabbitMQ | Kafka |
|---|---|---|
| 定位 | 通用消息中间件 | 分布式流平台 |
| 吞吐 | 中等 | 极高 |
| 消息模型 | 交换机/队列路由 | 分区日志（可回溯） |
| 适用 | 业务解耦、灵活路由 | 大数据量、日志、事件流 |

## 二、搜索（Elasticsearch）

**本质**：数据库 `LIKE` 全文检索太慢，ES 用**倒排索引**（词 → 文档）实现毫秒级全文搜索。

- 倒排索引：词 → 文档，实现全文搜索
- 核心概念：索引/文档/分片/副本、分词器（IK 中文分词）
- 与数据库同步：canal 监听 binlog → MQ → ES
- 查询：match（分词匹配）vs term（精确匹配）、聚合分析

## 三、Docker：把环境一起打包，交付不再「我机器上能跑」

**本质**：镜像 = 只读模板（代码 + 依赖 + 配置），容器 = 运行实例，解决环境不一致。

```dockerfile
# 示例：Spring Boot 应用镜像
FROM eclipse-temurin:17-jre
COPY app.jar /app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

- 镜像 vs 容器：镜像只读模板，容器是运行实例
- 核心命令：`docker build/run/ps/exec/logs`、`docker-compose` 编排多服务
- 网络与数据卷：容器间通信、数据持久化

## 四、部署与运维：上线 + 看护

**本质**：服务上线后要能**定位问题**（Linux/Nginx）、**自动交付**（CI/CD）、**持续观察**（可观测）。

### Linux 基础

- 常用命令：`ps`、`top`、`netstat`、`curl`、`systemctl`、`tail -f`
- 排查流程：CPU 高 → top 定位进程 → 线程栈；磁盘满 → df/du；连接数 → ss/netstat

### Nginx

- 反向代理 + 负载均衡（upstream、轮询/权重/ip_hash）
- 静态资源服务与缓存配置
- HTTPS 配置、`location` 路由规则

### CI/CD

```
代码提交 → 触发流水线 → lint/测试 → 构建镜像 → 推送仓库 → 部署到服务器
```

- GitLab CI / GitHub Actions / Jenkins
- 蓝绿发布 / 金丝雀发布 / 滚动更新

### 可观测性（三件套）

| 维度 | 工具 |
|------|------|
| 日志 Logging | ELK / Loki |
| 指标 Metrics | Prometheus + Grafana |
| 链路追踪 Tracing | Jaeger / SkyWalking |

## 五、云原生方向：进一步弹性伸缩与治理

**本质**：从「手工运维单机」走向「声明式、自动伸缩、服务治理」。

- K8s：Pod、Deployment、Service、Ingress、HPA 自动伸缩
- Service Mesh：Istio 服务治理
- Serverless：按需运行，免运维

## 常见面试题

> 点击展开参考答案，先自测再看。

### 1. 如何保证消息队列不丢消息？

<details><summary>参考答案</summary>

一条消息要经历三段，每段都要保证：

- **生产端**：开启 ack 确认（Kafka `acks=all`），失败重试
- **Broker**：持久化 + 分区副本（leader 挂了 replica 顶上），不因宕机丢
- **消费端**：**手动 ack**，处理成功再确认，否则消息重投（配合幂等）

三段缺一不可，任何一段「自动 ack」都可能导致丢消息。

</details>

### 2. Kafka 为什么吞吐高？

<details><summary>参考答案</summary>

- **顺序写盘**：追加写日志，磁盘顺序写不慢于内存随机写
- **零拷贝**：`sendfile` 从内核页缓存直接发网卡，不经用户态拷贝
- **批量 + 压缩**：攒批发送、批量落盘，减少网络与 IO 次数
- **分区并行**：多分区多消费者并行消费，水平扩展

</details>

### 3. 如何保证消息消费的幂等性？

<details><summary>参考答案</summary>

MQ 保证的是「至少一次」，重复投递不可避免，所以消费端必须幂等：

- **唯一业务号 + 去重表/唯一索引**：消费前查去重表，处理过则跳过（最通用）
- **状态机校验**：状态只允许单方向流转，重复消息命中非法状态直接忽略
- **业务本身幂等**：如 `UPDATE SET status=1 WHERE id=?` 天然幂等

</details>

### 4. Docker 镜像分层机制？为什么镜像小？

<details><summary>参考答案</summary>

- **分层**：Dockerfile 每条指令生成一层，层只读、可复用，相同层在多个镜像间共享，也加快构建（缓存）
- **镜像小**：① 层复用，共享基础层；② 多阶段构建（编译阶段 + 运行阶段分离，只留产物）；③ 精简基础镜像（如 alpine、jre 而非完整 jdk）

</details>

### 5. 生产环境服务响应慢，如何排查？

<details><summary>参考答案</summary>

按「网络 → 应用 → 依赖」逐层定位：

1. **网络/入口**：`curl` 测延迟，Nginx 日志看耗时，确认是入口慢还是后端慢
2. **应用层**：`top` 看 CPU；`jstack`/线程栈看是否锁等待、线程池打满；内存看 GC 日志
3. **依赖层**：慢 SQL 日志（`EXPLAIN` 定位）、Redis 慢查询、下游接口耗时
4. **全链路**：SkyWalking/Jaeger 看链路，定位耗时在哪个 span
5. **复现**：压测复现 + 监控指标对比，确认是容量问题还是偶发

</details>
