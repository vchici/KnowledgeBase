# Redis 消息队列

> List 做队列的两个坑（空转、丢消息）见[初步问答](./初步问答.md)；Redis 实例自身丢不丢数据由持久化决定，见[持久化](./持久化.md)。

## 一、List 方案：能用，但缺两样东西

`LPUSH` 生产 + `BRPOP` 阻塞消费，是小场景标准做法。但它是「裸队列」：

- **无消费确认**：`BRPOP` 取走即删，消费者处理到一半宕机，消息蒸发
- **无重投**：没有「这条消息处理成功了吗」的记录，谈不上重试

结论：允许极小概率丢消息的非核心场景才用 List。

## 二、Stream：补齐 ack 与重投

| 能力 | List | Stream |
|------|:---:|:---:|
| 消息持久留存 | 取走即删 | 保留，可回溯（`XRANGE`） |
| 消费确认 | 无 | `XACK` |
| 宕机恢复 | 无 | PEL（Pending Entries List）+ `XCLAIM` 重投 |
| 多消费者分组 | 手动分 | 消费者组 `XREADGROUP` 自动负载 |

可靠消费的完整动作：

1. `XADD` 写入消息，自动生成 ID
2. 消费者组内 `XREADGROUP` 读取 → 消息进入该消费者的 PEL（待确认列表）
3. 处理成功 → `XACK` 确认，消息移出 PEL
4. 消费者宕机未 ack → 消息留在 PEL；重启后 `XAUTOCLAIM` 认领其他消费者积压的待确认消息重投

效果：**至少一次投递**。配合消费端幂等（唯一键去重），就是可靠的队列。

## 三、不丢任务的完整链路

Redis 队列只是一环，端到端不丢靠三层：

1. **Redis 实例层**：持久化开 AOF（everysec），否则重启队列清空；要可用性再上主从 + 哨兵
2. **入队层**：任务先落库（任务表写 `PENDING`）再入队——队列丢了还能从任务表恢复，任务表才是真相源
3. **消费层**：处理完更新任务状态；重复投递由幂等挡住（唯一索引 / 去重键）

顺序不能反：**先落库再入队**。反过来入队成功、落库前宕机，任务就无影无踪。

## 四、选型

| 方案 | 可靠性 | 适用 |
|------|--------|------|
| 任务表 + 轮询 | 最高（状态即库，天然不丢） | 单机、量小、不想引入组件 |
| Redis List + BRPOP | 低（无 ack） | 通知、日志类，允许偶丢 |
| Redis Stream | 中高（ack + PEL 重投） | 轻量可靠队列，不想部署 MQ |
| Kafka / RocketMQ | 最高 | 核心业务、高吞吐、需要回溯 |

选型原则：可靠性要求和业务重要程度匹配，不为小工具上 Kafka，也不给核心交易用 List。
