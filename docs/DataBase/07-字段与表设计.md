# 07-字段与表设计

> 一句话本质：字段选型决定"每一列怎么存得对、存得省"，表设计决定"数据拆成几张表、怎么关联"——顺序是**先建模 → 再选字段 → 后拆表定索引**，反着来必返工。

前六章（[01-数据库架构](./01-数据库架构.md) ~ [06-数据库日志](./06-数据库日志.md)）讲的是"库怎么跑"，本篇讲"表怎么建"。上半场字段选型，下半场表结构设计。

## 上半场：字段选型

### 1. 字符 ≠ 字节

字段是表中的"列"，`char(10)` / `varchar(10)` 定义类型和长度；一个**字符**占多少**字节**，取决于字符集：

| 编码 | 1 字符占几字节 | 说明 |
|------|------|------|
| ASCII | 1 字节 | 仅英文 |
| UTF-8 | 英文/数字 1 字节，常用汉字 **3 字节** | 最常用 |
| utf8mb4 | Emoji **4 字节** | 支持表情包，MySQL 建表默认选它 |

### 2. char 与 varchar

| | char | varchar |
|---|---|---|
| 长度 | 固定，不足**补空格**，永远占满 N 字符 | 可变，按实际内容存 |
| 容量 | 0~255 字符 | 理论上限 65535 字符 |
| 适用 | 长度几乎固定的短值（国家码、哈希值） | 长度不定的名称、标题 |

### 3. BLOB 与 TEXT：大字段的分工

- **BLOB** 存二进制（图片、音频、证书、序列化对象）；**TEXT** 存大文本（文章、日志、JSON 串）。

BLOB 的典型场景：

| 场景 | 为什么用 BLOB |
|------|------|
| 加密密钥 / SSL 证书 / 二进制 Token | 本身就是无规律字节流，不适合文本表示 |
| 游戏玩家镜像数据 | 几百种属性序列化（Protobuf）成一条 BLOB，读写一条记录，免几十次 JOIN |
| Session 持久化 | 登录态序列化加密后存 BLOB，实现分布式登录 |
| SQLite 本地库 | 无网/离线场景，头像小图标直接存本地 |

TEXT 的典型场景：

| 场景 | 说明 |
|------|------|
| 富文本（HTML/Markdown） | 长文 + 排版代码轻松超过 varchar 的 65535 字节，LONGTEXT 可到 4GB |
| 日志 / 审计 / 原始报文 | 体积大、只查不筛，塞 TEXT 扔后台 |
| JSON 配置快照 | 个性化设置、审批流节点、订单商品快照（防商家改数据） |
| AI 时代的 Prompt / 对话历史 | 几千字的提示词模板、多轮上下文、RAG 召回文档 |

**核心区别：行内 vs 行外存储（Row Overflow）**

- `VARCHAR` 是**行内存储**：整行一起读进内存，多个大 varchar 即便没填满也占数据页空间 → 一页能放的行变少，查询效率下降。
- `TEXT` 是**行外存储**：行内只留约 10 字节**指针**，正文藏在专门的数据页；`SELECT` 没查它就完全不占行内存，查了才顺指针去捞。

TEXT 避坑三条：

1. **不要对 TEXT 做 `ORDER BY` / `GROUP BY`**——内存放不下，直接落**磁盘临时表**；要排序用时间/ID 字段。
2. **避免 `SELECT *`**——不小心带出 TEXT 字段会消耗大量带宽和 I/O。
3. **不能建普通索引**——内容模糊搜索上 Elasticsearch，或退而求其次用 `FULLTEXT` 全文索引。

### 4. DATETIME 与 TIMESTAMP

一句话：**TIMESTAMP 时区敏感，DATETIME 时区无感**。东八区插入 `2026-06-12 12:00:00`，东京（东九区）用户读取：

- `DATETIME`：还是 `12:00:00`——字面值，像"本子上写的字"，谁看都一样。
- `TIMESTAMP`：变成 `13:00:00`——写入时按当前时区转 **UTC** 存储，读取时再转成连接时区显示。

致命隐患：**2038 问题（Y2K38）**。TIMESTAMP 只有 4 字节（有符号整型），最大只能表示到 **2038-01-19 03:14:07**，之后溢出崩溃。存合同期限、出生日期这类长周期数据绝对不能用。

选型结论（业界主流，如阿里规范）：**默认 DATETIME**——支持到 9999 年、存取所见即所得（对账查日志不踩时区坑）、5.6.4+ 优化后仅 5 字节，与 TIMESTAMP 的 4 字节差距可忽略。

### 5. 货币字段：DECIMAL 还是 BIGINT？

先排除 `FLOAT` / `DOUBLE`：浮点数有精度误差（`0.1 + 0.2 ≠ 0.3`），碰钱就是事故。

- **电商、账单类**：用 `DECIMAL(19,4)`（精确定点数，19 位数字、4 位小数）。

```sql
CREATE TABLE orders (
    id INT AUTO_INCREMENT,
    amount DECIMAL(19,4),
    PRIMARY KEY (id)
);
```

- **银行支付类**：用 `BIGINT`，把金额乘以固定因子（×100 变"分"）存整数，展示时再除回去。为什么银行业更爱 BIGINT？

| 维度 | BIGINT | DECIMAL(19,4) |
|------|--------|---------------|
| 计算 | CPU 原生整数指令，纳秒级 | 软件层逐位模拟计算，海量批处理慢数倍 |
| 存储 | 固定 8 字节 | 约 9 字节以上，索引/`SUM`/`GROUP BY` 效率更低 |
| 跨语言 | 各语言都对应 `long`/`int64`，RPC/JSON 传输不失真 | Java 映射 `BigDecimal`、Go 用第三方库，误转 `double` 精度即崩 |
| 业务直觉 | 对账 = "数硬币"，资金变动就是整数个最小单位的转移 | — |

## 下半场：表设计原则

### 6. 关系建模：三种关系落表方式固定

| 关系 | 落表方式 | 例子 |
|------|---------|------|
| 一对一 | 合成一张表，或拆表隔离大字段/低频字段 | 用户 ↔ 用户详情 |
| 一对多 | 拆两张表，「多」的一方存「一」的外键 | 订单 ↔ 订单项 |
| 多对多 | 中间表存双方外键，中间表本身是业务数据 | 学生 ↔ 课程（选课表） |

判断标准：问「**一条 A 对应几条 B**」，而不是凭感觉。

### 7. 拆表信号：出现才拆，没出现别拆

单表几千行就拆表是过度设计。信号：

- **一对多关系**：一次主记录对应多条子记录，必须拆子表，否则只能往一个字段里塞数组/JSON，无法索引和约束
- **写入互相影响**：高频写的子数据和低频主数据混在一起互相拖慢
- **访问模式不同**：列表页只用几个字段，详情页才用大字段——拆出去免得拖累行宽（呼应 TEXT 行外存储）
- **单表过大**：行数千万级，或单行太宽导致数据页放不下几行

### 8. 拆表方式

| 方式 | 做法 | 适用 |
|------|------|------|
| 垂直拆（按列） | 主表留核心小字段，大字段/低频字段拆扩展表 | 行很宽、字段访问频率差异大 |
| 水平拆（按行） | 按时间、hash 把行分到多表/多库 | 单表行数千万级以上 |
| 按业务拆 | 不同业务域各自建表，ID 关联 | 微服务、模块边界清晰 |

### 9. 范式与反范式

- **范式（3NF）**：每个事实只存一份，靠 JOIN 关联——不冗余、更新不出脏数据，代价是查询要 JOIN。
- **反范式**：故意冗余（订单表存商品名称**快照**）——少 JOIN 读得快、还留了历史快照，代价是更新要同步多处。

选择标准：**读多写少要快 → 允许冗余；写多要强一致 → 严格范式**。电商订单存商品快照就是典型的反范式 + 快照，防止源数据被改后对不上。

### 10. 建表基本规范

- 主键：自增 `BIGINT` 或分布式 ID；不用业务字段（手机号、身份证会变）
- 关联字段：子表外键列与父表主键**类型一致**；物理外键约束一般不建（拖慢写入），靠应用层保证
- 高频查询条件（如 `device_id + created_at`）设计时就规划**联合索引**，别等慢查询再补（索引原理见 [02-数据库索引](./02-数据库索引.md)）
- 状态字段用 `TINYINT` 存枚举，不用 `VARCHAR`
- 每张表带 `created_at` / `updated_at`，排查问题必备

## 面试问答

### VARCHAR 和 TEXT 的本质区别？

<details><summary>参考答案</summary>
行内 vs 行外存储。VARCHAR 的内容随整行一起读入数据页，定义过大即使用不满也挤占页空间，降低一页能放的行数；TEXT 行内只存约 10 字节指针，正文放行外页，不查询就不产生 I/O。代价是 TEXT 不能建普通索引、不能直接 ORDER BY/GROUP BY（会落磁盘临时表），所以短文本首选 VARCHAR，长且不定长的富文本/日志/JSON 快照才用 TEXT。
</details>

### DATETIME 和 TIMESTAMP 怎么选？

<details><summary>参考答案</summary>
核心差异是时区：TIMESTAMP 写入转 UTC、读取按连接时区换算（时区敏感），DATETIME 存字面值（时区无感）。TIMESTAMP 只有 4 字节，最大表示到 2038-01-19 03:14:07（Y2K38 问题），长周期业务会溢出。现代 MySQL 的 DATETIME 仅 5 字节，空间劣势可忽略，因此业界规范默认 DATETIME；只有确需数据库自动做时区换算且时间范围确定在 2038 前的场景才考虑 TIMESTAMP。
</details>

### 什么时候拆表？怎么拆？

<details><summary>参考答案</summary>
信号驱动：出现一对多关系、写入互相影响、大小字段访问模式不同、单表行数到千万级，才考虑拆；没信号拆表是过度设计。方式三种：垂直拆按列把大字段/低频字段移出主表，水平拆按行分表分库应对单表过大，按业务拆对应微服务边界。拆之前先做关系建模（一对一合并/一对多外键/多对多中间表），再权衡范式与反范式：读多写少允许冗余快照，写多强一致走严格范式。
</details>

### 银行核心系统为什么用 BIGINT（分）而不是 DECIMAL？

<details><summary>参考答案</summary>
四点：① BIGINT 走 CPU 原生整数运算，DECIMAL 要软件模拟逐位算，海量批处理/日终对账慢数倍；② BIGINT 固定 8 字节更省，索引和 SUM/GROUP BY 吞吐更高；③ BIGINT 跨语言就是 int64，RPC/序列化不失真，DECIMAL 各语言映射不同库，误转 double 即丢精度；④ 银行业务资金变动本质是整数个最小货币单位（分/厘）的转移，整数对账更直觉。
</details>
