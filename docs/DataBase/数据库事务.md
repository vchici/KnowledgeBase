# 数据库事务

> 以 InnoDB 为准。事务依赖的三种日志（Redo / Undo / Binlog）与两阶段提交见[数据库日志](./数据库日志.md)。

## 一、ACID 与各自的实现

| 特性 | 含义 | 靠什么实现 |
|------|------|-----------|
| 原子性 Atomicity | 一组操作要么全成功，要么全回滚 | **Undolog**：记录修改前旧值，回滚时反向执行 |
| 一致性 Consistency | 数据从一个合法状态到另一个合法状态 | 由下面三者共同保证，是最终目的 |
| 隔离性 Isolation | 并发事务互不干扰 | **MVCC + 锁** |
| 持久性 Durability | 提交后断电也不丢 | **Redolog**：WAL，先写日志再刷数据页 |

记忆：A、I、D 是手段，C 是结果。原子性就是「失败整体回滚」——比如一段体检要写结果记录、更新段状态、更新体检汇总三步，包在一个事务里，任何一步失败全部撤销，不会留下写了一半的脏数据。

## 二、并发事务的三类问题

| 问题 | 现象 |
|------|------|
| 脏读 | 读到了别的事务**未提交**的数据，对方回滚后你的数据就是假的 |
| 不可重复读 | 同一事务内两次读同一行，值变了（别人 update 并提交了） |
| 幻读 | 同一事务内两次范围查询，行数变了（别人 insert 并提交了） |

## 三、四个隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|------|:---:|:---:|:---:|------|
| 读未提交 RU | 可能 | 可能 | 可能 | 基本没人用 |
| 读已提交 RC | 解决 | 可能 | 可能 | 每条语句生成一次 Read View；PG / Oracle 默认 |
| 可重复读 RR | 解决 | 解决 | 见下 | **InnoDB 默认**；事务开始时生成一次 Read View |
| 串行化 | 解决 | 解决 | 解决 | 读加共享锁，并发最差 |

- InnoDB 的 RR 下，快照读靠 MVCC 不产生幻读；当前读（`SELECT ... FOR UPDATE`、`UPDATE`）靠**间隙锁（Next-Key Lock）**锁住范围防插入
- 选择：绝大多数业务用默认 RR；对一致性要求不高、追求并发的报表类场景可用 RC

## 四、MVCC 一句话

每行数据带隐藏列（事务 ID + 回滚指针），沿 Undolog 串成**版本链**；事务读时按自己的 Read View 判断哪个版本对自己可见 —— 实现「读不加锁、读写不阻塞」。

- **RC**：每条 SELECT 都生成新 Read View → 能看到别人刚提交的 → 不可重复读
- **RR**：只在事务第一次读时生成一次 → 整个事务读到的都是同一快照 → 可重复读

细节（版本链怎么走、长事务为什么危险）见[数据库日志](./数据库日志.md)的 Undolog 部分。

## 五、使用事务的原则

- **事务要短**：事务里不要放 RPC 调用、文件 I/O 等慢操作，锁和 Undolog 都要持有到提交
- 嵌套业务拆成小事务，失败靠重试 / 补偿，而不是开一个包住全流程的大事务
- 本地场景同理：SQLite 同样支持事务，`BEGIN ... COMMIT` 保证一段结果的原子写入；配合 WAL 模式读写不互斥
- 只有一行写入时不需要显式开事务，单条语句本身就是原子的
