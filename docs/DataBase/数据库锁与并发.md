# 数据库锁与并发

> 并发访问数据库时怎么协调「读」和「写」。隔离级别与 MVCC 见[数据库事务](./数据库事务.md)，InnoDB 的 Redolog WAL 见[数据库日志](./数据库日志.md)。

## 一、为什么读写会互斥

- 写操作在改数据，读操作要求看到一致视图，同一份数据的并发访问必须协调
- 协调手段只有两种：**阻塞**（加锁等待）或 **多版本**（MVCC，让读读旧版本，根本不碰正在写的数据）
- InnoDB 普通 SELECT 靠 MVCC 实现读写不互斥；SQLite 靠 WAL 模式实现，思路同样是「读写各自的数据文件」

## 二、InnoDB 的锁体系

| 锁 | 粒度 / 作用 |
|----|------------|
| 全局锁 | 整库只读，用于逻辑备份（FTWRL） |
| 表锁 / MDL | 表级；MDL 防止查询期间表结构被改 |
| 意向锁 | 表级标记「表里有行锁」，让表锁操作不用逐行检查 |
| 行锁 Record Lock | 锁单行（走索引才生效，索引失效会退化成锁全表扫描过的行） |
| 间隙锁 Gap Lock | 锁区间，防止插入，RR 级别当前读防幻读 |
| Next-Key Lock | Record + Gap，RR 当前读的实际加锁单位 |

共享锁 S（`LOCK IN SHARE MODE`）与排他锁 X（`FOR UPDATE`）兼容规则：S-S 兼容，S-X、X-X 互斥。

- **默认读写不互斥**：普通 SELECT 是快照读，不加锁；只有「写与写」「当前读与写」之间互斥
- **死锁**：事务 A 等 B 的锁、B 等 A 的锁；InnoDB 自动检测并回滚代价小的一方。避免：按固定顺序访问资源、事务尽量短

## 三、SQLite 的锁模型（本地单文件库，与 InnoDB 不同）

| 模式 | 写入方式 | 并发表现 |
|------|---------|---------|
| rollback journal（默认） | 改页前把原页复制到 journal 文件 | **读写互斥**：写时读阻塞、读时写阻塞 |
| WAL 模式 | 写追加到 `-wal` 文件，主文件不动，checkpoint 时合并 | **读写不互斥**：读的照常读主文件，写的往 wal 里追加；仍是**单写者**（写写互斥） |

本地工具的典型用法：分析线程负责写、UI 线程负责读，开 WAL 后互不卡顿。

注意点（面试可讲）：

- WAL 只解决读写互斥，**写仍然要串行**——多线程写要么排队，要么收敛到单写线程
- 配套参数：`PRAGMA journal_mode=WAL`、`busy_timeout`（拿不到锁等多久再报错）、`synchronous=NORMAL`（WAL 下的常规选择）
- `-wal` 文件会持续增长，依赖 checkpoint；正常关闭连接会自动合并

> 不要把两个 WAL 混为一谈：InnoDB 的 WAL 指「先写 Redolog 再刷数据页」的持久化策略；SQLite 的 WAL 指 journal 模式，是并发模型。共同点都是「写进独立的日志/追加文件，读者不碰正在写的部分」。

## 四、多线程访问数据库的原则

- **写收敛**：写操作走单线程或串行队列（SQLite 尤其如此），读可多线程并发
- **事务要短**：锁持有时间 = 事务时长，事务里不放 RPC、文件 I/O
- **连接数与并发度匹配**：本地工具 1 个写连接 + 按需读连接足够，服务端按 `CPU/IO` 配置连接池
- **拿不到锁要有策略**：设超时 + 重试，而不是无限等
