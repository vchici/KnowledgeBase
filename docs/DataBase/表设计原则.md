# 表设计原则

> 顺序：先建模（实体和关系）→ 再决定拆不拆表 → 最后定主键、字段、索引。字段类型的选择见[数据库字段](./数据库字段.md)。

## 一、关系建模

实体之间的三种关系，落表方式固定：

| 关系 | 落表方式 | 例子 |
|------|---------|------|
| 一对一 | 合成一张表，或拆表隔离大字段 / 低频字段 | 用户 ↔ 用户详情 |
| 一对多 | 拆两张表，「多」的一方存「一」的一方的外键 | 体检记录 ↔ 体检段；订单 ↔ 订单项 |
| 多对多 | 中间表存双方外键，中间表本身就是业务数据 | 学生 ↔ 课程（选课表） |

判断标准：**问「这条数据一条 A 对应几条 B」**，而不是凭感觉。

## 二、什么时候拆表

一张表出现以下信号就该拆，没出现就别拆（单表几千行拆表是过度设计）：

- **一对多关系**：一次主记录对应多条子记录（如一次体检多个段），必须拆子表，否则要在一个字段里塞数组 / JSON，无法索引和约束
- **写入互相影响**：高频写的子数据和低频的主数据混在一张表，互相拖慢
- **访问模式不同**：列表页只用几个字段，详情页才用大字段（TEXT / JSON），拆出去避免拖累行宽（见 [TEXT 行外存储](./数据库字段.md)）
- **单表过大**：行数到千万级、或单行很宽导致数据页能放的行变少

## 三、拆表的方式

| 方式 | 做法 | 适用 |
|------|------|------|
| 垂直拆（按列） | 主表留核心小字段，大字段 / 低频字段拆到扩展表 | 行很宽、字段访问频率差异大 |
| 水平拆（按行） | 按时间、hash 等把行分到多张表 / 多个库 | 单表行数太大（千万级以上） |
| 按业务拆 | 不同业务域各自建表，通过 ID 关联 | 微服务、模块边界清晰 |

多段体检的例子属于第一种场景的组合：一对多必须拆，同时每段结果数据量大、增长快，也符合按业务拆出独立结果表。

## 四、范式与反范式

- **范式（3NF）**：每个事实只存一份，靠 JOIN 关联。优点是不冗余、更新不出脏数据；代价是查询要 JOIN
- **反范式**：故意冗余（如订单表里存商品名称快照）。优点是少 JOIN、读得快，还能留历史快照；代价是更新要同步多处

选择标准：**读多写少、要快 → 允许冗余；写多、数据要强一致 → 严格范式**。电商订单存商品快照就是典型的反范式 + 快照，防止源数据被改。

## 五、建表基本规范

- 主键：用自增 BIGINT 或分布式 ID，不用业务字段（手机号、身份证会变）
- 关联字段：子表外键列 + 父表 ID，类型和父表主键一致；是否建物理外键约束看团队规范，互联网业务一般不建（影响写入性能），靠应用层保证
- 每个 `device_id + created_at` 这类高频查询条件，设计时就规划联合索引，不要等慢查询了再补
- 状态类字段（如任务状态）用 TINYINT 存枚举值，不用 VARCHAR
- 每张表带 `created_at` / `updated_at`，排查问题必备
