# 数据库日志面试题

> 基于 [数据库日志](数据库日志.md) 整理，覆盖 Binlog / Redolog / Undolog 三大日志。点击展开参考答案，先自测再看。

## 一、基础概念题

### 1. MySQL 的三种日志分别属于哪个层级、记录什么内容、核心作用是什么？

<details><summary>参考答案</summary>

| 日志 | 层级 | 类型 | 写入时机 | 核心作用 |
|------|------|------|---------|---------|
| Binlog | Server 层（所有引擎共用） | 逻辑日志 | 事务提交时 | 主从复制、数据恢复、CDC |
| Redolog | InnoDB 引擎层 | 物理日志（页的修改） | 事务执行中持续写 | 崩溃恢复（crash-safe） |
| Undolog | InnoDB 引擎层 | 逻辑日志（修改前旧值） | 修改数据前 | 事务回滚、MVCC |

一句话：Redolog 保证"已提交的不丢"，Undolog 保证"未提交的可回滚 + 读不到未提交的"，Binlog 保证"主从数据一致"。

</details>

### 2. Binlog 和 Redolog 默认开启吗？

<details><summary>参考答案</summary>

- **Binlog 默认关闭**，需要在 `my.cnf` 中配置 `log-bin=mysql-bin` 开启
- **Redolog 必需**，InnoDB 不可关闭（否则无法 crash-safe）

</details>

### 3. Binlog 有哪三种写入格式？各有什么优缺点？MySQL 5.7+ 默认哪种？

<details><summary>参考答案</summary>

| 格式 | 记录内容 | 优点 | 缺点 |
|------|---------|------|------|
| `STATEMENT` | 原始 SQL 语句 | 日志量小 | 函数（`NOW()`、`UUID()`）在从库重放结果不一致 |
| `ROW` | 每行数据变更的前后镜像 | 精确，无歧义 | 日志量大 |
| `MIXED` | 自动选择，一般用 STATEMENT，遇不安全函数切 ROW | 兼顾大小与精度 | 判断逻辑复杂 |

MySQL 5.7+ 默认 `ROW`。这也是 Canal 等 CDC 工具能解析出"哪行变成什么"的前提。

</details>

### 4. Undolog 记录什么？INSERT / DELETE / UPDATE 分别记录什么反向操作？

<details><summary>参考答案</summary>

Undolog 记录"**如何撤销这次修改**"（修改前的旧值），与 Redolog 的"如何重做"正好相反：

| 操作 | Undolog 记录的反向操作 |
|------|----------------------|
| `INSERT` | `DELETE`（删除刚插入的行） |
| `DELETE` | `INSERT`（恢复被删除的行） |
| `UPDATE` | `UPDATE`（改回旧值） |

</details>

## 二、机制原理题（为什么类）

### 5. 为什么 Binlog 和 Redolog 需要"两份"？只用一份不行吗？

<details><summary>参考答案</summary>

- Redolog 是**引擎层**的，保证崩溃恢复，但只在单机有效
- Binlog 是 **Server 层**的，用于主从复制/数据恢复/CDC，但写入时机晚于事务执行，没有 crash-safe 能力
- 两者职责不同、缺一不可，通过**两阶段提交**协调

</details>

### 6. 描述两阶段提交的三个步骤。崩溃恢复时如何判断一个事务该提交还是回滚？

<details><summary>参考答案</summary>

三步：

```
1. 写 Redolog（prepare 状态）   ── 存储引擎层
2. 写 Binlog                   ── Server 层
3. 写 Redolog（commit 状态）    ── 存储引擎层
```

崩溃恢复时以 **Binlog 是否写入**为准：
- Binlog 已写入 → 提交事务（认为事务已成功）
- Binlog 未写入 → 回滚事务

这样保证从库重放 Binlog 时与主库状态严格一致。

</details>

### 7. 什么是 WAL？为什么"先写日志再写数据页"能提升性能还能保证不丢数据？

<details><summary>参考答案</summary>

WAL（Write-Ahead Logging）= 先写 Redolog 并落盘，再修改内存中的数据页，数据页异步刷盘。

**提速原因**：
- 数据页是**随机写**（页分散在磁盘各处），慢
- Redolog 是**顺序写**（追加到文件尾部），快
- 本质是把"随机写"转化为"顺序写"，事务提交只需等 Redolog 落盘

**不丢数据原因**：
- 崩溃时数据页可能没落盘，但 Redolog 已落盘
- 重启后重放 Redolog，把未落盘的数据页恢复出来

</details>

### 8. Redolog 为什么是循环写而不是像 Binlog 一样无限追加？write pos 和 checkpoint 是什么关系？

<details><summary>参考答案</summary>

Redolog **固定大小、循环写入**（可覆盖旧日志），Binlog 无限追加、按大小切换文件（不可覆盖，要留着做复制/恢复）。

- `write pos`：下一条日志的写入位置，不断前移
- `checkpoint`：已刷盘边界，刷盘后前移，跟在 write pos 后面追
- 两者之间是"**未刷盘**"区域——崩溃恢复的关键（日志已写、数据页未落盘）
- 当 write pos 快追上 checkpoint（空闲耗尽）→ 必须停下强制刷盘推进 checkpoint → **业务停顿**

所以大事务场景要调大 `innodb_log_file_size`。

</details>

### 9. `innodb_flush_log_at_trx_commit` 三个值分别是什么行为？如何取舍？

<details><summary>参考答案</summary>

| 值 | 行为 | 安全性 | 性能 |
|----|------|--------|------|
| `0` | 每秒由后台线程刷盘 | 最低（崩溃丢 1 秒） | 最高 |
| `1` | 每次事务提交都 fsync 刷盘 | 最高（不丢数据） | 最低 |
| `2` | 每次提交写 page cache，每秒刷盘 | 中（OS 崩溃才丢） | 中 |

默认/生产推荐 `1`。

</details>

### 10. 什么是"双 1 配置"？为什么单独开一个"1"不够？

<details><summary>参考答案</summary>

双 1 = `innodb_flush_log_at_trx_commit=1`（Redolog 每次提交落盘）+ `sync_binlog=1`（Binlog 每次提交落盘），是 MySQL 数据安全的黄金标准。

因为两者通过两阶段提交协作，单独开一个：

- 只开 Redolog 的 1：主库能恢复，但 Binlog 没落盘 → 从库丢数据 → 主从不一致
- 只开 Binlog 的 1：从库能同步，但 Redolog 没落盘 → 主库丢数据 → 主从不一致
- 双 1：主库可恢复 + 从库可同步，主从严格一致

代价：每次提交 2 次 fsync，最安全但最慢。高并发可降级（`=2` + `sync_binlog=100`），金融交易必须双 1。

</details>

### 11. 双 1 降级为 `=2 + sync_binlog=100` 后，MySQL 进程被 kill 和服务器断电分别会丢什么？

<details><summary>参考答案</summary>

- **MySQL 进程崩溃（被 kill）**：page cache 仍在 OS 内核 → **不丢数据**
- **OS 崩溃/断电**：page cache 丢失 → Redolog 丢 1 秒、Binlog 丢最多 100 个事务 → **主从不一致**

降级提速原理：fsync 涉及磁盘寻道很慢，降级后每次提交只写内存，性能可提升数倍到数十倍。

</details>

### 12. 描述 InnoDB 崩溃恢复的完整流程。Undolog 在其中扮演什么角色？

<details><summary>参考答案</summary>

```
1. 读取 Redolog，找到 checkpoint 位置
2. 重放 checkpoint 之后的 Redolog（已提交 + 未提交的事务都重放）
3. 用 Undolog 回滚未提交的事务
4. 数据恢复到崩溃前已提交的状态
```

配合两阶段提交：Redolog 处于 prepare 状态时崩溃 → 查 Binlog，已写入则 commit，未写入则 rollback（用 Undolog 回滚）。

Undolog 的角色：Redolog 会把未提交事务也重放出来，需要靠 Undolog 的反向操作把它们撤销掉，实现"已提交的保留，未提交的回滚"。

</details>

### 13. MVCC 中 Undolog 起什么作用？RC 和 RR 隔离级别的 Read View 有什么区别？

<details><summary>参考答案</summary>

Undolog **为读操作提供历史版本**：

- 事务 A 未提交的修改（age 30，旧值 20 在 Undolog）
- 事务 B 读时当前值不可见 → 沿 Undolog **版本链**找到旧版本 age=20（可见）→ 返回 20

Read View 生成时机的区别：
- **RC（读已提交）**：每条 SELECT 都生成新的 Read View → 总能读到最新已提交版本
- **RR（可重复读）**：事务开始时生成一次 → 整个事务读到的版本固定

</details>

### 14. Undolog 什么时候真正删除？为什么长事务是危险的？

<details><summary>参考答案</summary>

Undolog **不是事务提交就删除**——要等没有其他事务依赖它的旧版本时，purge 线程才清理。

长事务的危害（不结束 → 它的 Undolog 无法 purge）：
- Undo 表空间膨胀
- 历史版本链变长，查询性能下降
- 占用大量内存

</details>

## 三、场景应用题

### 15. 描述 MySQL 主从复制的完整流程。

<details><summary>参考答案</summary>

主库写好 Binlog 后：

1. 从库的 **IO Thread** 连接主库，拉取 Binlog
2. 先存入本地中转站 **Relay Log**（中继日志）
3. 从库的 **SQL Thread** 照着 Relay Log 重放操作
4. 从库数据随之更新，与主库保持一致

```
主库（写操作）→ Binlog → IO Thread → Relay Log → SQL Thread → 从库数据
```

</details>

### 16. 今天 14:00 误删了一张表，如何把数据恢复到误删前一刻？

<details><summary>参考答案</summary>

数据恢复 = **备份打底 + Binlog 重放增量**：

1. 先恢复昨晚的全量备份（Binlog 只记增量，得先有底子）
2. 用 `mysqlbinlog` 重放"昨晚备份 → 13:59"之间的 Binlog，补上备份后的全部业务操作
3. 用 `--stop-position` **停在误删语句之前**，跳过 DROP
4. 数据回到误删前一秒，之后丢失的写入需人工补

关键理解：
- Binlog 是二进制文件，`mysqlbinlog` 负责翻译成 SQL，管道 `| mysql` 负责重新执行
- `--stop-datetime` 按时间截取（粒度粗），`--stop-position` 按字节偏移截取（精确到单条语句，误删恢复必用）

</details>

### 17. Canal 为什么能拿到 MySQL 的数据变更？Canal → MQ → 消费者 → Redis 链路上各环节保证什么？

<details><summary>参考答案</summary>

**Canal 伪装成从库**：主从复制协议不校验从库身份，Canal 按协议和主库握手，主库就把 Binlog 推给它，Canal 实时解析出"哪张表哪行变成什么"。

链路各环节的可靠性职责：

| 环节 | 保证 |
|------|------|
| Canal → MQ | ack 前位点不前进 → 不丢 |
| MQ 内部 | 落盘持久化 + 失败重投 + 死信 → 必达（削峰、一对多广播） |
| 消费者 → Redis | `DEL key` 幂等，重复消费安全 → 可重试 |
| Redis | 读时 miss 回填，永远以 DB 为准 → 最终一致 |

</details>

### 18. CDC 方案里，为什么收到变更后是"删缓存"而不是"写缓存"？为什么用 Binlog 订阅而不是业务代码删？

<details><summary>参考答案</summary>

**删而不写**：并发写到达顺序可能与 DB 提交顺序不一致，SET 旧值会覆盖新值；`DEL` 是幂等且对顺序不敏感的，下次读 miss 时自然回填 DB 最新值。

**订阅 Binlog 而不是业务代码删**：
- 业务代码里"更新 DB 后顺手 DEL"这一步可能失败（网络抖动、进程挂），脏数据要等到缓存过期才消除
- Binlog 是 MySQL 落盘的持久化流水，**不依赖业务代码**；Canal 挂了重启从位点续传，一条变更都漏不掉

</details>

### 19. 一次 UPDATE 执行过程中，三种日志分别在什么时机写入？

<details><summary>参考答案</summary>

以 `UPDATE user SET age=30 WHERE id=1` 为例：

```
修改数据前 → 写 Undolog（旧值，用于回滚/MVCC）
修改数据时 → 写 Redolog（物理修改，用于崩溃恢复）
事务提交时 → 写 Binlog（逻辑变更，用于复制/CDC）
                     │
                     ▼
              两阶段提交（Redolog prepare → Binlog → Redolog commit）
```

</details>
