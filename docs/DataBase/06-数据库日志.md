# 06-数据库日志

> 一句话本质：三种日志各守一道防线——Undolog 保证「未提交的可回滚」，Redolog 保证「已提交的不丢」，Binlog 保证「主从一致」；WAL 把随机写变顺序写，两阶段提交把两层日志绑成一个整体。

ACID 靠它们实现（见 [04-数据库事务](./04-数据库事务.md)）；崩溃恢复的工程实践见 [08-任务状态与崩溃恢复](./08-任务状态与崩溃恢复.md)。本章正文讲机制，19 道面试题折叠并入对应小节（编号沿用题库）。一次 UPDATE：改数据前写 Undolog（回滚/MVCC）→ 执行中持续写 Redolog（崩溃恢复）→ 提交时写 Binlog（复制/CDC），后两者走两阶段提交。
## 〇、全局观：三种日志一张表
| 日志 | 层级 | 类型 | 写入时机 | 核心作用 |
|------|------|------|---------|---------|
| Binlog | Server 层（所有引擎共用） | 逻辑日志 | 事务提交时 | 主从复制、数据恢复、CDC |
| Redolog | InnoDB 引擎层 | 物理日志（页的修改） | 事务执行中持续写 | 崩溃恢复（crash-safe） |
| Undolog | InnoDB 引擎层 | 逻辑日志（修改前旧值） | 修改数据前 | 事务回滚、MVCC |
## 一、Binlog：归档日志（Server 层）

记录所有**已提交**的写操作，逻辑日志、与存储引擎无关；事务提交后写入，先写 page cache 再 fsync 落盘；**默认关闭**，`my.cnf` 中 `log-bin=mysql-bin` 开启；`binlog_format = STATEMENT | ROW | MIXED`，MySQL 5.7+ 默认 `ROW`（Canal 等 CDC 能解析行变更的前提）。

| 格式 | 记录内容 | 优点 | 缺点 |
|------|---------|------|------|
| `STATEMENT` | 原始 SQL 语句 | 日志量小 | 函数（`NOW()`、`UUID()`）在从库重放结果不一致 |
| `ROW` | 每行数据的变更前后镜像 | 精确，无歧义 | 日志量大（批量操作产生大量行记录） |
| `MIXED` | 自动选择，一般用 STATEMENT，遇不安全函数切 ROW | 兼顾大小与精度 | 判断逻辑复杂 |
### 2. Binlog 和 Redolog 默认开启吗？
<details><summary>参考答案</summary>

- **Binlog 默认关闭**，需要 `my.cnf` 配置 `log-bin=mysql-bin` 开启；**Redolog 必需**，InnoDB 不可关闭（否则无法 crash-safe）
</details>

### 3. Binlog 有哪三种写入格式？各有什么优缺点？MySQL 5.7+ 默认哪种？
<details><summary>参考答案</summary>

`STATEMENT` 记原始 SQL，日志量小，但函数（`NOW()`、`UUID()`）在从库重放结果不一致；`ROW` 记每行变更前后镜像，精确无歧义但日志量大；`MIXED` 自动切换。MySQL 5.7+ 默认 `ROW`。
</details>

**主从复制**：主库写好 Binlog 后，从库 IO 线程连主库拉取，先存本地中转站 Relay Log，再照着中继日志重放，实现数据同步。

### 15. 描述 MySQL 主从复制的完整流程。
<details><summary>参考答案</summary>

主库（写操作）→ Binlog → 从库 **IO Thread** 拉取 → 存入本地中转站 **Relay Log**（中继日志）→ 从库 **SQL Thread** 照着 Relay Log 重放 → 从库数据随之更新，与主库保持一致。
</details>

```bash
mysqlbinlog --start-datetime="2025-01-01 00:00:00" --stop-datetime="2025-01-01 12:00:00" mysql-bin.000123 | mysql -u root -p
mysqlbinlog --start-position=154 --stop-position=1024 mysql-bin.000123 | mysql -u root -p   # Binlog 是二进制文件，mysqlbinlog 翻译成可执行 SQL；按字节偏移更精确
```

### 16. 今天 14:00 误删了一张表，如何把数据恢复到误删前一刻？
<details><summary>参考答案</summary>

数据恢复 = **备份打底 + Binlog 重放增量**：先恢复昨晚全量备份（Binlog 只记增量，得先有底子）→ 用 `mysqlbinlog` 重放「昨晚备份 → 13:59」之间的 Binlog → 用 `--stop-position` **停在误删语句之前**跳过 DROP → 数据回到误删前一秒，之后丢失的写入人工补。`--stop-datetime` 按时间截取（粒度粗），`--stop-position` 按字节偏移（精确到单条语句，误删恢复必用）。
</details>

**CDC 数据同步（缓存一致性）**：主库不区分从库身份，Canal 伪装成从库按协议握手拿 Binlog，实时解析表行变更，异步更新 Redis 缓存（详见 [Redis 数据更新](./Redis/数据更新.md)）：`MySQL 写入 → 产生 Binlog → Canal 解析 → DEL Redis / 写入 MQ`。

### 17. Canal 为什么能拿到 MySQL 的数据变更？Canal → MQ → 消费者 → Redis 链路上各环节保证什么？
<details><summary>参考答案</summary>

**Canal 伪装成从库**：主从复制协议不校验从库身份，Canal 按协议握手，主库就把 Binlog 推给它，实时解析出「哪张表哪行变成什么」。链路各环节：Canal → MQ 靠 ack 前位点不前进保证不丢；MQ 内部靠落盘持久化 + 失败重投 + 死信保证必达（削峰、一对多广播）；消费者 → Redis 靠 `DEL key` 幂等，重复消费安全可重试；Redis 读时 miss 回填，永远以 DB 为准 → 最终一致。
</details>

### 18. CDC 方案里，为什么收到变更后是「删缓存」而不是「写缓存」？为什么用 Binlog 订阅而不是业务代码删？
<details><summary>参考答案</summary>

**删而不写**：并发写到达顺序可能与 DB 提交顺序不一致，SET 旧值会覆盖新值；`DEL` 幂等且对顺序不敏感，下次读 miss 时自然回填 DB 最新值。**订阅 Binlog**：业务代码「更新 DB 后顺手 DEL」可能失败（网络抖动、进程挂），脏数据要等缓存过期才消除；Binlog 是 MySQL 落盘的持久化流水，不依赖业务代码，Canal 挂了重启从位点续传，一条变更都漏不掉。
</details>

## 二、Redolog：重做日志（引擎层，crash-safe 的基石）

InnoDB 引擎层的**物理日志**，记录「哪个数据页的哪个偏移改成了什么」；事务执行中持续写入，**必需、不可关闭**，保证已提交事务不丢失。

**WAL 机制（Write-Ahead Logging）**：先写日志，再写数据页——写 Redolog 落盘（顺序写，快）→ 修改内存数据页 → 异步落盘。**快**在把数据页的随机写（页分散磁盘各处）转化为日志的顺序写（追加文件尾部），提交只等 Redolog 落盘；**不丢**是因为崩溃时数据页可能没落盘但 Redolog 已落盘，重启重放即恢复。
### 7. 什么是 WAL？为什么「先写日志再写数据页」能提升性能还能保证不丢数据？
<details><summary>参考答案</summary>

WAL = 先写 Redolog 并落盘，再修改内存中的数据页，数据页异步刷盘。**提速**：数据页是随机写（页分散在磁盘各处）慢，Redolog 是顺序写（追加文件尾部）快，本质是把随机写转化为顺序写，事务提交只需等 Redolog 落盘。**不丢**：崩溃时数据页可能没落盘，但 Redolog 已落盘，重启后重放把数据页恢复出来。
</details>

**循环写结构：write pos 与 checkpoint**——Binlog 无限追加、按大小切换文件，Redolog 则固定大小、循环写入：

```
┌──────────────────┬──────────────────────────────────┬──────────────┐
│      已刷盘       │     未刷盘（待恢复用，不可覆盖）      │     空闲      │
└──────────────────┴──────────────────────────────────┴──────────────┘
  checkpoint ↑（已刷盘边界，之前可覆盖）    write pos ↓（下一条将写在这里）
```

- 两者**同向移动**：write pos 在前写新日志，checkpoint 在后追赶（刷盘后前移）；两者之间「未刷盘」区域是**崩溃恢复的关键**（日志已写、数据页还在内存未落盘）
- write pos 快追上 checkpoint（空闲耗尽，日志写满）→ 必须停下强制刷盘推进 checkpoint → **业务停顿**，大事务要调大 `innodb_log_file_size`（配 `innodb_log_files_in_group=2` 共 2G）
### 8. Redolog 为什么是循环写而不是像 Binlog 一样无限追加？write pos 和 checkpoint 是什么关系？
<details><summary>参考答案</summary>

Redolog **固定大小、循环写入**（旧日志可覆盖），Binlog 无限追加、按大小切换文件（不可覆盖，要留着做复制/恢复）。`write pos` 是下一条日志的写入位置，不断前移；`checkpoint` 是已刷盘边界，刷盘后前移、跟在后面追；两者之间是「**未刷盘**」区域——崩溃恢复的关键（日志已写、数据页未落盘）。write pos 快追上 checkpoint（空闲耗尽）→ 必须停下强制刷盘推进 checkpoint → 业务停顿，所以大事务场景要调大 `innodb_log_file_size`。
</details>

**刷盘策略**：`innodb_flush_log_at_trx_commit` 控制 Redolog 何时从 page cache 真正写盘——`0` 每秒后台刷（崩溃丢 1 秒，最快）；`1` 每次提交 fsync（不丢数据，最慢，默认/生产推荐）；`2` 每次提交写 page cache 每秒刷（OS 崩溃才丢）。

**双 1 配置** = `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`（Binlog 每次提交落盘），MySQL 数据安全的黄金标准：前者保主库崩溃后可恢复、后者保从库正确同步，只开一个都会主从不一致（见两阶段提交）；最安全但最慢（每次提交 2 次 fsync），高并发可降级 `=2` + `sync_binlog=100`，金融交易必须坚持双 1。
### 9. `innodb_flush_log_at_trx_commit` 三个值分别是什么行为？如何取舍？
<details><summary>参考答案</summary>

`0` 每秒由后台线程刷盘，崩溃丢 1 秒数据，性能最高；`1` 每次事务提交都 fsync，不丢数据，最慢，默认 / 生产推荐；`2` 每次提交写 page cache、每秒刷盘，OS 崩溃才丢。按业务对数据安全的要求取舍。
</details>

### 10. 什么是「双 1 配置」？为什么单独开一个「1」不够？
<details><summary>参考答案</summary>

双 1 = `innodb_flush_log_at_trx_commit=1`（Redolog 每次提交落盘）+ `sync_binlog=1`（Binlog 每次提交落盘）。两者通过两阶段提交协作，单独开一个：只开 Redolog 的 1 → 主库能恢复，但 Binlog 没落盘，从库丢数据；只开 Binlog 的 1 → 从库能同步，但 Redolog 没落盘，主库丢数据；双 1 才能主库可恢复 + 从库可同步，主从严格一致。代价：每次提交 2 次 fsync，最安全但最慢。
</details>

### 11. 双 1 降级为 `=2 + sync_binlog=100` 后，MySQL 进程被 kill 和服务器断电分别会丢什么？
<details><summary>参考答案</summary>

**MySQL 进程崩溃（被 kill）**：page cache 仍在 OS 内核 → **不丢数据**；**OS 崩溃 / 断电**：page cache 丢失 → Redolog 丢 1 秒、Binlog 丢最多 100 个事务 → **主从不一致**。降级提速原理：fsync 涉及磁盘机械寻道很慢，降级后每次提交只写内存，性能可提升数倍到数十倍。
</details>

**崩溃恢复（crash-safe）**：读 Redolog 找到 checkpoint 位置 → 重放 checkpoint 之后的 Redolog（已提交 + 未提交的事务都重放）→ 用 Undolog 回滚未提交的事务 → 数据恢复到崩溃前已提交的状态。
### 12. 描述 InnoDB 崩溃恢复的完整流程。Undolog 在其中扮演什么角色？
<details><summary>参考答案</summary>

读 Redolog 找到 checkpoint 位置 → 重放 checkpoint 之后的 Redolog（已提交 + 未提交的事务都重放）→ 用 Undolog 回滚未提交的事务 → 数据恢复到崩溃前已提交的状态。配合两阶段提交：Redolog 处于 prepare 状态时崩溃 → 查 Binlog，已写入则 commit，未写入则 rollback。Undolog 的角色：Redolog 会把未提交事务也重放出来，要靠 Undolog 的反向操作把它们撤销，实现「已提交的保留，未提交的回滚」。
</details>

## 三、两阶段提交：Redolog × Binlog 的协作

Binlog 与 Redolog 分属两层、职责不同缺一不可——Redolog 管引擎层崩溃恢复（仅单机有效），Binlog 管 Server 层复制 / 恢复 / CDC（写入时机晚于事务执行，没有 crash-safe 能力）；通过**两阶段提交**保证一致性，避免主从数据错乱：

```
1. 写 Redolog（prepare 状态）   ── 存储引擎层
2. 写 Binlog                   ── Server 层
3. 写 Redolog（commit 状态）    ── 存储引擎层
```

崩溃恢复时以 **Binlog 是否写入**为准：已写入 → 提交事务（认为事务已成功）；未写入 → 回滚事务（认为事务未成功）。这样从库通过 Binlog 重放时，能与主库状态严格一致。
### 5. 为什么 Binlog 和 Redolog 需要「两份」？只用一份不行吗？
<details><summary>参考答案</summary>

- Redolog 是**引擎层**的，保证崩溃恢复，但只在单机有效；Binlog 是 **Server 层**的，用于主从复制 / 数据恢复 / CDC，但写入时机晚于事务执行，没有 crash-safe 能力
- 两者职责不同、缺一不可，通过**两阶段提交**协调
</details>

### 6. 描述两阶段提交的三个步骤。崩溃恢复时如何判断一个事务该提交还是回滚？
<details><summary>参考答案</summary>

三步：写 Redolog（prepare 状态）→ 写 Binlog → 写 Redolog（commit 状态）。崩溃恢复以 **Binlog 是否写入**为准：已写入 → 提交事务（认为事务已成功）；未写入 → 回滚事务。这样保证从库重放 Binlog 时与主库状态严格一致。
</details>

## 四、Undolog：回滚日志（引擎层，回滚 + MVCC）

InnoDB 引擎层的逻辑日志，记录数据修改前的旧值；**事务提交后不立即删除**，等没有读事务依赖时才清理。反向操作：INSERT → 记 `DELETE`（删刚插入的行）；DELETE → 记 `INSERT`（恢复被删的行）；UPDATE → 记改回旧值的 `UPDATE`。
### 4. Undolog 记录什么？INSERT / DELETE / UPDATE 分别记录什么反向操作？
<details><summary>参考答案</summary>

Undolog 记录「**如何撤销这次修改**」（修改前的旧值），与 Redolog 的「如何重做这次修改」正好相反：INSERT → 记 `DELETE`（删除刚插入的行）；DELETE → 记 `INSERT`（恢复被删除的行）；UPDATE → 记改回旧值的 `UPDATE`。
</details>

**作用一：事务回滚**——执行失败或 `ROLLBACK` 时，用 Undolog 反向操作恢复数据：
```sql
UPDATE account SET balance = balance - 100 WHERE id = 1;  -- 写 Undolog（旧值 balance=500）
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- 写 Undolog（旧值 balance=200）
ROLLBACK;  -- InnoDB 读 Undolog 反向恢复：id=1 改回 500，id=2 改回 200
```
**作用二：MVCC 多版本读（最容易被忽略但极重要）**——为读操作提供历史版本：事务 A 未提交的修改（age=30，旧值 20 存入 Undolog），事务 B 读时当前值不可见，沿版本链找到可见旧版本：`当前数据(30) → Undolog v2(20) → v1(18)`，由 Read View 判断可见性。RC 与 RR 的区别只在 Read View 生成时机：RC 每条 SELECT 生成新的 → 总读最新已提交；RR 事务开始时生成一次 → 整个事务读同一快照。
### 13. MVCC 中 Undolog 起什么作用？RC 和 RR 隔离级别的 Read View 有什么区别？
<details><summary>参考答案</summary>

Undolog **为读操作提供历史版本**：事务 A 未提交的修改（age 30，旧值 20 在 Undolog），事务 B 读时当前值不可见 → 沿 Undolog **版本链**找到旧版本 age=20（可见）→ 返回 20。Read View 生成时机：**RC** 每条 SELECT 都生成新的 → 总能读到最新已提交版本；**RR** 事务开始时生成一次 → 整个事务读到的版本固定（可重复读）。
</details>

**生命周期与 purge 线程**：提交后没有其他事务依赖 → purge 线程清理；还有事务在读旧版本 → 保留到其结束。配置：`innodb_undo_logs=128`（回滚段）、`innodb_max_undo_log_size=1G`、`innodb_undo_log_truncate=ON`（自动回收）。**长事务的危害**：长事务不结束，它的 Undolog 无法 purge → Undo 表空间膨胀、历史版本链变长查询变慢、占用大量内存。
### 14. Undolog 什么时候真正删除？为什么长事务是危险的？
<details><summary>参考答案</summary>

Undolog **不是事务提交就删除**——要等没有其他事务依赖它的旧版本时，purge 线程才清理。长事务的危害（不结束 → 它的 Undolog 无法 purge）：Undo 表空间膨胀、历史版本链变长查询性能下降、占用大量内存。
</details>

## 五、三日志协作全景
```
修改数据前        修改数据时         提交时              崩溃恢复
写 Undolog       写 Redolog       写 Binlog          重放 Redolog
(回滚/MVCC)      (崩溃恢复)       (复制/CDC)         + Undolog 回滚未提交
                                    └── 两阶段提交（Redolog prepare → Binlog → commit）
```
**一句话总结**：Redolog 保证「已提交的不丢」；Undolog 保证「未提交的可回滚」+「读不到未提交的」；Binlog 保证「主从数据一致」。

### 1. MySQL 的三种日志分别属于哪个层级、记录什么内容、核心作用是什么？
<details><summary>参考答案</summary>

Binlog：Server 层逻辑日志，事务提交时写，用于主从复制、数据恢复、CDC；Redolog：InnoDB 引擎层物理日志，事务执行中持续写，用于崩溃恢复（crash-safe）；Undolog：InnoDB 引擎层逻辑日志，修改数据前写，用于事务回滚、MVCC。一句话：Redolog 保证「已提交的不丢」，Undolog 保证「未提交的可回滚 + 读不到未提交的」，Binlog 保证「主从数据一致」。
</details>

### 19. 一次 UPDATE 执行过程中，三种日志分别在什么时机写入？
<details><summary>参考答案</summary>

以 `UPDATE user SET age=30 WHERE id=1` 为例：修改数据前写 Undolog（旧值，用于回滚 / MVCC）→ 修改数据时写 Redolog（物理修改，用于崩溃恢复）→ 事务提交时写 Binlog（逻辑变更，用于复制 / CDC），Redolog 与 Binlog 之间走两阶段提交（prepare → Binlog → commit）。
</details>
