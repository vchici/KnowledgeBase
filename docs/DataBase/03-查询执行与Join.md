# 03-查询执行与Join

> 一句话本质：Join 的本质是双重 for 循环——外层循环次数由驱动表（外表）决定，内层循环代价由内表索引决定；「小表驱动大表 + 被驱动表关联字段建索引」就是这两句话的工程落地。

[01-数据库架构](./01-数据库架构.md) 讲了 SQL 在架构里怎么流转，[02-数据库索引](./02-数据库索引.md) 讲了单表怎么查得快。本章讲两件事：SQL 的逻辑执行顺序，以及优化器怎么执行多表 Join。

## 一、一条 SQL 的三步解析

查询语句在真正执行前要过三关：

| 阶段 | 干什么 |

| 语义分析 | 检查表、列是否存在，进行权限验证 |

## 二、书写顺序 ≠ 执行顺序

| 执行顺序 | 关键字 | 作用 |
|---------|--------|------|
| ① | FROM | 确定主表，准备数据 |
| ② | ON | 连接多个表的条件 |
| ③ | JOIN | 执行 INNER JOIN / LEFT JOIN 等 |
| ④ | WHERE | 过滤行数据（越早过滤，后面处理量越小） |
| ⑤ | GROUP BY | 分组 |
| ⑥ | HAVING | 过滤聚合后的数据 |
| ⑦ | SELECT | 选择最终返回的列 |
| ⑧ | DISTINCT | 去重 |
| ⑨ | ORDER BY | 对最终结果排序 |
| ⑩ | LIMIT | 限制返回行数 |

- WHERE 先执行是为了**尽早减少数据量**；HAVING 只能过滤聚合结果；ORDER BY 排的是最终结果；LIMIT 最后执行以减少数据传输。这也解释了 **SELECT 里定义的别名为什么不能在 WHERE 里用**——WHERE 跑在 SELECT 之前。

## 三、IN vs EXISTS：两条执行路线

设外表 `A`（用户表）、内表 `B`（订单表）。

```python
# IN：先查内表缓存，再遍历外表
B_list = select_all_from_B()      # 先把子查询查完，结果缓存在内存
for a in A:
    if a.id in B_list: print(a)   # 在内存中比对

# EXISTS：先遍历外表，逐条代入子查询
for a in A:
    # 每条外表记录执行一次子查询，找到一条满足的 B 就立刻返回 True
    if has_any_match_in_B(a.id): print(a)
```

| 场景 | 首选 | 原因 |
|------|------|------|
| 外表大、内表小 | `IN` | 内表小，全量缓存进内存；外表走索引来内存比对，效率极高 |
| 外表小、内表大 | `EXISTS` | 只循环外表的次数；内表关联字段有索引时，每次循环都是索引精准命中，不用加载内表全量数据 |

**NULL 陷阱（前面加 NOT 后致命）：**

| 写法 | 子查询结果集包含 NULL 时 |
|------|------------------------|
| `NOT IN` | **整个查询直接返回空集**——任何值与 NULL 等值比较结果都是 Unknown，整条判断失效 |
| `NOT EXISTS` | 只关心「有没有行返回」，返回一条含 NULL 的记录也算有数据 → 不受 NULL 影响 |

> 💡 **避坑铁律**：无法保证子查询的列 100% 没有 NULL，一律用 `NOT EXISTS` 代替 `NOT IN`。

```sql
-- IN：子查询只返回单列
SELECT * FROM User
WHERE id IN (SELECT user_id FROM Orders WHERE price > 100);

-- EXISTS：习惯写 SELECT 1，且必须包含两表的关联条件
SELECT * FROM User u
WHERE EXISTS (
    SELECT 1 FROM Orders o
    WHERE o.user_id = u.id AND o.price > 100  -- 必须有关联条件
);
```

（`SELECT 1` / `SELECT *` / `SELECT id` 性能没有任何区别——EXISTS 只看有没有行，不看列的值，业界习惯写 `1`。）

## 四、Join 的本质：双重 for 循环

```python
for x in Table_A:          # 外层循环：Table_A 就是“外表”
    for y in Table_B:      # 内层循环：Table_B 就是“内表”
        if x.id == y.id:
            print(match)
```

- **外表（Outer / 驱动表）**：放外层循环，数据库先读它，一条条吐数据去触发内层查询。
- **内表（Inner / 被驱动表）**：放内层循环，外表每吐一条，它就被动匹配一次。

新手疑问：反正都要两两匹配，总次数不都是 A×B 吗？**差距不在循环次数，而在内层循环能不能走索引**：

| 场面 | 外表 | 内表（有索引） | 总消耗 |
|------|------|------|--------|
| ① | 100 条 | 100 万条 | 100 次循环 × 每次 3~4 次 I/O → 瞬间完成 |
| ② | 100 万条 | 100 条 | 100 万次外层循环 + 100 万次内层查找 → 明显变慢甚至卡死 |

**核心结论**：先查哪个表（谁当驱动表），决定了哪张表享受「被索引精准降维打击」的福利——被反复查找的内表必须有索引。

## 五、小表驱动大表

- 目的：**减少外层循环次数**——小表当外表（驱动表），大表（带索引）当内表（被驱动表）。
- 「小表」不是 `COUNT(*)` 小，而是 **WHERE 过滤后参与实际循环的结果集更小**：

```sql
-- A 有 100 万行，B 有 10 万行；但“今天刚注册”的可能只有 50 条
SELECT * FROM A JOIN B ON A.id = B.a_id WHERE A.status = '今天刚注册';
```

此时 A 过滤后只有 50 条 ≪ B 的 10 万条，优化器会选 **A 做驱动表**。

## 六、外表索引 vs 内表索引：分工截然不同

**ON 阶段，外表索引形同虚设**：外表要做的第一件事是「把数据一条条全拿出来」，没有过滤条件就得全表扫描——索引的本质是帮你「少读数据」，而你现在要读「所有数据」，外表有没有索引都改变不了它要循环 N 次的宿命。内表相反：外表每吐一个 id（比如 5），内表就执行一次 `WHERE user_id = 5`，内表索引被疯狂调用。

**WHERE 阶段，外表索引是生死线**：

```sql
SELECT * FROM User u JOIN Order o ON u.id = o.user_id
WHERE u.status = 'active' AND u.age > 30;   -- 外表的过滤条件
```

有索引时 MySQL 不会全表扫 User，而是用 `status` / `age` 上的索引精准抓人：100 万行过滤到 100 行，**外层循环从 100 万次暴跌到 100 次**。没索引，第一步就卡死。

| | 外表（驱动表）索引 | 内表（被驱动表）索引 |
|--|------------------|---------------------|
| 职责 | **瘦身**：配合 WHERE 过滤，减少外层循环次数 | **拦截**：等值匹配，避免内表全表扫描 |
| 生效条件 | 写了 `WHERE 外表字段 = xxx` 才有用 | 只要是两表关联（`ON a.id = b.a_id`）就必须生效 |
| 缺失后果 | 第一步全表扫描，整条 SQL 卡死 | 每条外表数据触发一次内表全扫，O(N×M) 灾难 |

## 七、非等值匹配：范围可以，不等不行

关联条件不止等值，还可能是 `>`、`<`、`!=`、`BETWEEN...AND` 甚至 `LIKE`。

**范围匹配——内表索引有用，但要 Range Scan**：

```sql
-- 每笔订单落在哪个促销活动期间
SELECT o.order_id, o.order_time, c.campaign_name
FROM Orders o
JOIN Campaigns c
  ON o.order_time BETWEEN c.start_time AND c.end_time;  -- 非等值匹配
```

内表 `start_time` 建了 B+ 树索引就能快速定位到第一个满足条件的活动，不用全表扫描；但它是范围查找，得顺着叶子链表做一段**范围扫描（Range Scan）**，不能像等值那样「瞬间精准抓取一条」。

**不等值匹配（`!=` / `<>`）——索引直接失效**：

```sql
-- 找薪资相同、但不在同一部门的员工组合（薪酬公平性分析）
SELECT e1.name, e2.name, e1.salary
FROM Staff e1
JOIN Staff e2
  ON e1.salary = e2.salary AND e1.department_id != e2.department_id;
```

B+ 树的强项是告诉你「谁在哪里」，无法高效告诉你「谁不等于谁」。若内表条件里纯粹只有 `!=`（如 `ON a.name != b.name`），外表每吐一条数据，内表都得全表扫描一遍——O(N×M) 灾难。

**连锁反应：Hash Join 失效，退化为 BNL**：

1. **Hash Join 只能用于等值匹配**。等值时，MySQL 8.0 / PostgreSQL 会把小表在内存里建成哈希表，大表一扫瞬间匹配，连内表索引都不需要；一旦用 `>`、`<`、`!=`，哈希值算不了，这个暴风级的优化手段直接失效。
2. 非等值 + 没有合适的范围索引 → 只能退回 **Block Nested Loop（BNL）**：外表的一批数据读进 Join Buffer，然后全表扫描内表，在内存里逐条比对是否满足 `BETWEEN` 或 `!=`。

**避坑指南**：

1. 能等值尽量等值——必要时加辅助字段，把非等值转换成等值；
2. 范围关联（`ON a.time BETWEEN b.start AND b.end`）**内表的范围字段（如 start）必须建索引**，否则大表关联瞬间卡死。

## 八、都无索引时：为什么还是小表驱动大表

无索引时 MySQL 用 BNL，绝不会傻到每读一条外表数据就扫一遍内表，真实操作是：

- **小表驱动大表（A→B）**：小表 100 条一次性塞进 Join Buffer → 大表**只全表扫描 1 次**，每条进内存跟缓冲区里整批比对。磁盘 I/O 极低。
- **大表驱动小表（B→A）**：Join Buffer（默认几百 KB）装不下大表，只能分批——塞 1 万条 → 扫一遍小表 → 清空 → 再塞下一批……**内表（小表）被迫重复全表扫描很多次**，磁盘 I/O 暴涨。

> **结论**：即使没有索引，小表驱动大表也能让驱动表尽量一次装进内存，极大减少内表的扫描次数。
>
> **开发者唯一要做的**：通过 WHERE 把某张表过滤到最小，并确保另一张被关联表的关联字段有索引。剩下的，优化器比我们想象的聪明得多。

## 面试问答

### IN 和 EXISTS 的区别？怎么选？

<details><summary>参考答案</summary>

- **IN**：先执行子查询把内表结果缓存进内存，再遍历外表比对——先内后外。
- **EXISTS**：先遍历外表，每条记录代入子查询执行一次，只要有行返回就算 True——先外后内；子查询习惯写 `SELECT 1`，必须带关联条件。
- 选型：外表大内表小用 IN（内表缓存 + 外表走索引）；外表小内表大用 EXISTS（循环次数少 + 内表索引精准命中）。本质都是小表驱动大表。
- NULL 陷阱：子查询结果含 NULL 时 `NOT IN` 直接返回空集（NULL 比较为 Unknown），`NOT EXISTS` 不受影响——不确定有无 NULL 一律用 `NOT EXISTS`。

</details>

### 内外表的顺序是我写 SQL 决定的，还是 MySQL 决定的？

<details><summary>参考答案</summary>

现代 MySQL 采用 **CBO（基于成本的优化器）**自动决定：不管你把哪张表写在前、用 JOIN 还是 LEFT / RIGHT JOIN（在不破坏业务逻辑的前提下），它都会计算各种方案的 CPU 和磁盘 I/O 成本，选「过滤后结果集最小」的表去驱动。早期数据库（如 Oracle 的 RBO 模式）才按 SQL 书写顺序执行。所以**写 SQL 不用刻意调换 JOIN 前后的表顺序**。

</details>

### 既然优化器自动选，为什么还要懂这些原理？

<details><summary>参考答案</summary>

三个优化器会「翻车」的场景：

1. **统计信息失真**（最常见）：MySQL 靠自己维护的统计信息估算表大小，不会每次执行都 COUNT(*)。表刚发生大规模增删改或统计过期，就可能误把大表当小表——需要手动 `ANALYZE TABLE` 更新统计信息，甚至用 `STRAIGHT_JOIN` 强行指定驱动顺序。
2. **复杂条件猜错**：WHERE 涉及多表多字段、存在多个联合索引时，成本计算可能陷入局部最优、选错驱动表。懂原理才能看懂 `EXPLAIN` 里的 `rows` 和 `Extra`，判断优化器是不是「变傻了」。
3. **指导建索引**：判断出 A 过滤后是小表、B 是大表，就立刻知道 **B 的关联字段必须建索引**，而不是盲目给两张表所有字段都建，浪费磁盘和写入性能。

</details>

### 大表没索引、小表有索引，该怎么驱动？

<details><summary>参考答案</summary>

让**有索引的小表当内表（被驱动表）**、无索引大表当外表：外表 10 万条逐条吐出，去小表（有索引）里找，总计算量约 10 万 × 3~4 次 ≈ 40 万次，远好于让无索引大表当内表（50 × 10 万 = 500 万次）。

但若两表是**等值匹配**，MySQL 8.0+ 根本不在这两个烂方案里二选一——直接上 **Hash Join**：小表加载进内存建哈希表，大表一次性全表扫描逐条比对，总计算量 = 扫一遍大表 + 内存哈希比对，完全绕开「谁当内表都没索引」的尴尬局面。

</details>

### 两表都没有索引时，Join 会怎么执行？

<details><summary>参考答案</summary>

走 **Block Nested Loop（BNL）**：把外表的一批数据装进 Join Buffer（默认几百 KB），内表每全表扫描一次，就能和缓冲区里整批数据在内存中比对。所以驱动表越小越能一次装完：**小表驱动 → 大表只扫 1 次**；大表驱动 → 缓冲区分批装，小表被迫重复扫描很多次。这就是「没有索引也强调小表驱动大表」的原因——减少内表的磁盘扫描次数。另外，等值场景下 MySQL 8.0+ 会优先用 Hash Join 替代 BNL。

</details>
