# 数据库索引

> 以 InnoDB 的 B+ 树索引为准。JOIN 时内外表索引的分工见[数据库查询](./数据库查询.md)，建表时怎么规划索引见[表设计原则](./表设计原则.md)。

## 一、为什么是 B+ 树

索引查询的成本 ≈ 树高 × 每层一次磁盘 I/O，选索引结构就是在压树高。

| 结构 | 问题 |
|------|------|
| 哈希表 | 只支持等值，不支持范围和排序 |
| 二叉树 / 红黑树 | 树太高，千万级数据要二十多次 I/O |
| B 树 | 非叶子节点也存数据，单页放不下几个键，树照样高 |
| B+ 树 | 非叶子只存键，叶子存数据且串成链表；千万级数据树高 3~4 层，范围查询顺着叶子链表扫 |

## 二、聚簇索引与回表

- **聚簇索引**：主键索引，叶子节点存整行数据，InnoDB 表本身就是按主键组织的 B+ 树
- **二级索引**（普通索引）：叶子节点只存「索引列 + 主键值」
- **回表**：走二级索引先拿到主键，再回聚簇索引查整行。`SELECT *` 配普通索引 = 命中多少条就回表多少次

## 三、联合索引与最左前缀

联合索引 `(a, b, c)` 的排序规则：先按 a 排，a 相同再按 b，b 相同再按 c —— 类似字典先按首字母再按第二个字母排。所以 **a 有序、a 相定时 b 才有序**，这就是最左前缀的全部原因。

| 查询条件 | 命中情况 |
|----------|---------|
| `a=1` / `a=1 AND b=2` / `a=1 AND b=2 AND c=3` | 完整命中 |
| `b=2` / `b=2 AND c=3` | 不命中（跳过 a，b 全表无序） |
| `a=1 AND c=3` | 只有 a 命中（a 相同的区间里 c 无序） |
| `a=1 AND b>10 AND c=3` | a、b 命中，c 失效（遇到范围，后续列无序） |

**列顺序怎么定：等值条件列在前，范围条件列在后。**

例：结果表建 `(device_id, start_time)` 联合索引，覆盖「查某台设备某段时间的结果」—— `device_id` 等值在前，`start_time` 范围在后，正好完整命中。

## 四、覆盖索引

查询要的列全部在索引里，不用回表：

- `SELECT start_time FROM result WHERE device_id = 1 AND start_time > '...'`：索引 `(device_id, start_time)` 本身就含这两列，直接返回
- 技巧：把常查的少数几列追加到联合索引尾部实现覆盖；但索引越宽写入越慢，别滥用

## 五、索引失效的常见场景

| 写法 | 为什么失效 |
|------|-----------|
| 对索引列做函数 / 运算：`WHERE YEAR(start_time) = 2026` | 树里存的是原始值，算过之后无从定位；改写成范围条件 |
| 隐式类型转换：字符串列写 `WHERE phone = 13800001111` | 等价于对列做 cast |
| 前导模糊：`LIKE '%abc'` | 前缀未知，找不到扫描起点（`'abc%'` 可以走） |
| `OR` 两侧有无索引的列 | 有一边走不了就全表扫 |
| `!=` / `NOT IN` | B+ 树只能定位区间，排除性条件只能扫 |

## 六、建索引的原则

- 给 WHERE / JOIN / ORDER BY 高频用到的列建，为「可能查」建索引只会拖慢写入
- 区分度高的列才值得建（性别这类建了也没用）
- 单表索引别太多：每个索引都是一棵要同步维护的 B+ 树
- 长字符串用前缀索引 `INDEX(email(20))`，减小索引体积
