# 任务状态与崩溃恢复

> 两层崩溃恢复要分开：**引擎层**是数据库自己不丢数据（Redolog / Undolog，见[数据库日志](./数据库日志.md)）；**应用层**是业务任务不丢进度（本篇：任务状态落库 + 断点续跑）。

## 一、问题：内存状态重启即丢

长流程任务（多段体检、批量导入、分步执行）如果进度只存在内存变量里，进程崩溃或重启后：

- 不知道做到哪一步
- 不知道哪些已完成
- 只能从头重跑，或干脆半途作废

解法一句话：**每一步的状态变更都写数据库，内存只是缓存**。重启后看库就知道进度。

## 二、任务表模式（最小实现）

一张任务表：`id`、类型、`status`、`retry_count`、时间戳。

- 状态流转：`PENDING → RUNNING → DONE / FAILED / CANCELLED`，本质就是 `status` 字段 + 流转校验（if/else），「状态机」只是这类写法的名字
- **先落库再执行**：接任务先写 `PENDING`，开跑前置 `RUNNING`，完成置 `DONE`——顺序不能反，先跑后记等于没记
- 状态更新和结果写入放**同一个事务**：否则「结果写了、状态没更新」的中间态崩溃后又是一笔糊涂账

## 三、崩溃后怎么续跑

重启时扫描任务表，按状态分流：

| 库里的状态 | 判断 | 处理 |
|-----------|------|------|
| `DONE` | 已完成 | 跳过 |
| `RUNNING` | **执行到一半，进度未知**（薛定谔态） | 复位重跑或跳过，靠幂等兜底 |
| `PENDING` | 还没跑 | 正常执行 |
| `FAILED` | 失败 | 进重试或失败列表 |

`RUNNING` 的薛定谔态是核心难点——崩溃时刻不知道执行到哪一步。两条路（可叠加）：

1. **细化状态粒度**：每个子步骤（每段体检）单独落库，恢复时精确到段
2. **任务幂等**：重跑不产生副作用（`task_id` 唯一索引防重复写入），这样「重跑」永远是安全的默认动作

## 四、任务表 = 最可靠的持久化队列

- 取任务 = 查 `PENDING` + 抢占：`UPDATE task SET status='RUNNING' WHERE id=? AND status='PENDING'`，更新到 1 行才继续——天然防多进程重复消费
- 对比 Redis 队列：任务表先落库，天然不丢；Redis 方案必须「先落库再入队、消费完更新状态」才能等价（见[项目包装-手机性能检测](../FullStack/项目包装-手机性能检测.md)）
- 两者可以组合：任务表管状态与恢复，Redis 管快速分发

## 五、适用边界

- **值得做**：流程长、执行有成本、恢复有价值（体检、导入、同步类任务）
- **不值得做**：一次性短操作——状态管理本身有成本，直接重试更省事
