# 08-任务状态与崩溃恢复

> 一句话本质：内存只是缓存，**每一步状态变更先落库**，崩溃后扫任务表按状态机分流续跑，重跑的安全性靠幂等兜底，兜不住的部分用重试和补偿收拾——终点是最终一致。

崩溃恢复有两层，别混：**引擎层**是数据库自己不丢数据（Redo/Undo，见 [06-数据库日志](./06-数据库日志.md)）；**应用层**是业务任务不丢进度，就是本篇。

## 一、问题：内存状态重启即丢

长流程任务（批量导入、分步执行）进度只放内存变量，进程一崩：不知道做到哪步、不知道哪些完成，只能从头重跑或半途作废。解法一句话：**每一步的状态变更都写数据库，重启后看库就知道进度。**

## 二、任务表模式（最小实现）

一张任务表：`id`、类型、`status`、`retry_count`、时间戳。三条铁律：

1. **状态流转**：`PENDING → RUNNING → DONE / FAILED / CANCELLED`，本质是 `status` 字段 + 流转校验（if/else），「状态机」只是这类写法的名字
2. **先落库再执行**：接任务先写 `PENDING`，开跑前置 `RUNNING`，完成置 `DONE`——顺序不能反，先跑后记等于没记
3. **状态更新和结果写入放同一个事务**：否则「结果写了、状态没更新」的中间态，崩溃后是一笔糊涂账（事务边界见 [04-数据库事务](./04-数据库事务.md)）

任务表本身就是**最可靠的持久化队列**。取任务 = 查 `PENDING` + 抢占：

```sql
UPDATE task SET status='RUNNING'
WHERE id=? AND status='PENDING';  -- 更新到 1 行才继续
```

天然防多进程重复消费。对比 Redis 队列：任务表先落库天然不丢；Redis 方案必须「先落库再入队、消费完更新状态」才等价。两者可组合：任务表管状态与恢复，Redis 管快速分发。

## 三、崩溃恢复：按状态分流

重启扫描任务表：

| 库里的状态 | 判断 | 处理 |
|-----------|------|------|
| `DONE` | 已完成 | 跳过 |
| `RUNNING` | **执行到一半，进度未知（薛定谔态）** | 复位重跑或跳过，靠幂等兜底 |
| `PENDING` | 还没跑 | 正常执行 |
| `FAILED` | 失败 | 进重试或失败列表 |

核心难点是 `RUNNING` 的薛定谔态——崩溃时刻不知道执行到哪一步。两条路（可叠加）：

1. **细化状态粒度**：每个子步骤单独落库，恢复时精确到段
2. **任务幂等**：重跑不产生副作用，让「重跑」永远是安全的默认动作

## 四、幂等、重试、补偿三件套

为什么单靠事务不够：事务的原子性边界 = 一次 `commit`，事务里放 RPC / 文件 I/O 会长期持锁，所以长流程必然拆成多个小事务；小事务各自成败，组合出**部分成功**——第 3 段失败时前 2 段已落库，回不去。能用的手段只有三个方向：**重来一次（重试）、重复无害（幂等）、撤销已做的（补偿）**。

### 幂等：让重复执行无害

同一操作执行一次和 N 次效果相同。必须有它，因为重试和 MQ 至少一次投递意味着**重复是常态不是异常**（MQ 见 [Redis/消息队列](./Redis/消息队列.md)）。

| 实现 | 原理 | 适用 |
|------|------|------|
| 唯一索引 / 唯一键 | 数据库层面拒绝重复插入（如结果表 `task_id`） | 插入类，**最可靠**，兜底永远在 DB |
| 状态机校验 | `UPDATE ... WHERE status='PENDING'` 更新到 0 行即被人抢先 | 任务 / 订单执行 |
| 乐观锁版本号 | `UPDATE ... SET v=v+1 WHERE v=?` | 更新类 |
| 天然幂等 | `DELETE by id`、`UPDATE 固定值` | 无需设计 |
| Token / Idempotency-Key | 先领号、执行时核销 | 前端防重复提交 |

坑：**先查后插有竞态**——查时不存在、插时别人已插。唯一索引 + 捕获冲突错误才是原子判断。

### 重试：对付瞬时失败

先分类：**瞬时失败**（网络抖动、锁冲突）自动重试能好；**永久失败**（参数非法、数据格式错）重试没用，快速失败进失败列表。三个关键参数：

1. **次数上限**：超过 N 次进死信/失败列表，不能无限循环
2. **退避**：指数退避 + 随机抖动，不要固定间隔
3. **前提幂等**：只重试幂等操作，否则重试 = 制造重复数据

重试风暴：下游抖一下、所有上游同时重试，流量放大数倍压垮下游 → 退避 + 抖动缓解，配合熔断限流止血。

### 补偿：对付不能重试的失败

流程第 N 步失败，前 N-1 步已各自提交、回滚不了（不是同一个事务）——**不回滚，再执行一个反向操作抵消已做的**：

- **Saga**：长事务拆成一串本地事务 `T1→T2→…→Tn`，每个 Ti 配反向补偿 Ci，某步失败逆序执行 C
- **TCC**：Try 预留资源 → Confirm / Cancel，多一步「预留」，适合扣库存、冻结余额这类不能事后硬撤的场景
- **本地消息表 / 事务消息**：业务数据和「待办消息」同一事务落库，异步推进，消费端幂等兜底，通用业务最常用

规则要事先明确：失败后是**中止**（逐段补偿）还是**跳过**（要有豁免理由、结果可查询），不能到现场再拍。

### 三件套怎么配合

失败 → 判断瞬时/永久 → 瞬时则幂等前提下的退避重试 → 超限进死信/失败列表 → 中途失败无法继续则补偿已完成部分。落地形态：MQ = 至少一次投递 + 消费端幂等；任务系统 = 任务表重试 + 死信；跨服务 = Saga / TCC / 本地消息表。

## 五、适用边界

- **值得做**：流程长、执行有成本、恢复有价值（导入、同步、检测类任务）
- **不值得做**：一次性短操作——状态管理本身有成本，直接重试更省事

## 面试问答

### 进程在任务 RUNNING 状态时崩溃，重启后怎么处理？

<details><summary>参考答案</summary>
RUNNING 是薛定谔态：崩溃时刻不知道执行到哪一步。分流策略是复位重跑或跳过，安全性靠两层保障：一是细化状态粒度，让每个子步骤单独落库、恢复精确到段；二是任务幂等（如结果表 task_id 唯一索引），保证重跑不产生副作用，使「重跑」成为安全默认动作。前提是任务本身「先落库再执行」，且状态更新与结果写入在同一个事务。
</details>

### 为什么重试必须配合幂等？常见幂等实现有哪些？

<details><summary>参考答案</summary>
重试和 MQ 至少一次投递使重复成为常态而非异常，非幂等操作一重试就制造重复数据。实现五类：唯一索引（插入类最可靠，兜底在 DB）、状态机校验（带条件的 UPDATE 抢占）、乐观锁版本号、天然幂等操作（DELETE by id / 更新固定值）、Token 机制（先领号再核销）。注意先查后插有竞态，唯一索引加捕获冲突错误才是原子判断。
</details>
