> 要理解 Spring，先得理解一个 HTTP 请求从浏览器进来、到返回响应的完整旅程。这段旅程的物理底座就是 **Servlet** 与 **Tomcat**：Tomcat 负责「接客」，Servlet 负责「办业务」。

# 一、Tomcat、Servlet、JSP / JSON 的物理关系

我们可以用一个「去办事大厅办事」的例子，彻底理清 **Tomcat、Servlet、JSP / JSON** 三者的物理关系：

- **Tomcat 是「办事大厅的物理建筑」：** 它负责开门、装空调、拉网线（监听端口、维护 TCP 连接）。但是它自己不会办业务。

- **Servlet 是「柜台里的业务员」：** 当一个市民（浏览器请求）冲进大厅，Tomcat 会根据你办的业务（URL），把你领到对应的柜台。**那个坐在柜台后面、真正听你诉求（解析参数）、帮你翻档案（查数据库）、给你办业务的 Java 类，就是 Servlet。**

- **JSP / JSON 是「办完业务给你的回执」：** 业务员把业务办好了，打印出一张表格（JSP 渲染成 HTML）或者给你一串代码（JSON 报文），让你带回家。

Servlet（Server Applet）就是一段运行在服务器（Tomcat）上的、专门用来处理网络请求的 Java 程序。

# 二、Servlet 的生命周期

Servlet 的生命周期由 Tomcat 容器统一管理，分三个阶段：

- `init()`（初始化，默认第一次请求时延迟加载）
- `service()`（处理请求，根据 HTTP 动词分发给 `doGet` / `doPost`）
- `destroy()`（销毁）

# 三、Servlet 的线程安全

**Servlet 绝不是线程安全的！**

Tomcat 对同一个 Servlet 类只创建一个单例。当 10000 个用户并发访问，Tomcat 会从线程池里分配 10,000 个物理线程，**同时并发执行这同一个 Servlet 实例的 `service()` 方法**。

这意味着：如果 Servlet 里写了实例字段（成员变量）来存请求相关的数据，多个线程会互相覆盖，产生数据错乱。请求数据应该放在方法局部变量里（栈上，线程私有），而不是实例字段里（堆上，多线程共享）。

# 四、Tomcat 的线程模型

Tomcat 靠堆砌操作系统线程来顶并发。它的潜意识里有几个假设：

- **资源是无限且独占的：** 物理机常年开着，启动慢一点（花 5 秒、10 秒）没关系，因为一年到头也重启不了几次。
- **内存可以尽情挥霍：** 物理机有的是内存，所以它启动时疯狂扫描所有的 Jar 包、预先创建几百个线程（每个线程吃 1MB 内存）常驻在内存里，觉得理所当然。

## 4.1 BIO 模式：Thread-per-request（一个请求一个操作系统内核线程）

当客户端（浏览器）向 Tomcat 发送连接请求时，Tomcat 会从线程池中分配一个线程伺候这个连接，负责：

```
读取网络数据 → 解析 HTTP 协议 → 执行 Servlet 代码（业务逻辑、查数据库）→ 组装响应 → 写回网络数据
```

Java 的线程在 JVM 底层是 1:1 映射到操作系统内核线程上的，有几个并发请求就会占用几个操作系统内核线程。

## 4.2 现代的 NIO 模式：NonBlocking IO

NIO 解决的是**网络等待和业务计算解耦**。

现代的 Tomcat 引入了多路复用技术，将网络连接和真正的业务处理解耦：

- **Acceptor & Poller 线程**：极少数的内核线程，利用操作系统的 epoll 机制，管住成千上万的网络连接。如果连接只是干挂着（keep-alive）不发数据，不需要占用专门的内核线程。
- **Worker 线程（工作线程池）**：当某个连接真正有 HTTP 请求数据传送过来，Poller 线程才会从线程池中抓 Worker 线程出来，把请求丢给它执行 Servlet。

执行完毕立刻回收——Servlet 执行完、数据返回给客户端了，Worker 线程立刻回到池子中伺候下一个连接，不需要等待连接断开。

## 4.3 虚拟线程（Virtual Threads）

虚拟线程解决的是**代码遇到阻塞 IO 时内核线程被白白占用**的问题。

当一个虚拟线程遇到阻塞的 IO 操作时，JVM 会直接把这个虚拟线程从内核线程上「卸载」下来，让宝贵的内核线程挂载另一个就绪的虚拟线程去干别的业务。等数据库的数据返回了，JVM 接收到通知，再把刚才放进内存歇着的虚拟线程重新「挂载」到任意一个空闲的内核线程上继续往下执行。

**一个请求对应一个 Java 虚拟线程，如果这个虚拟线程被阻塞，会自动让出内核线程，让内核线程去执行别的请求。**

# 五、Tomcat 的局限与演进

## 5.1 线程模型的局限

在高并发、或者 AI Agent 这种超长耗时的阻塞请求下，线程池会迅速耗尽，内存飙升。

**演进方向：** 现代架构改用 **Netty（异步非阻塞）**、**Go 语言协程（Goroutine）**，利用单线程事件循环（Epoll 机制）或极轻量的协程（只占几 KB），用极低的资源消耗顶住十几万连接。

## 5.2 冷启动阻碍了 Serverless

传统 Tomcat 启动时要高频扫描类路径、通过反射加载 Bean，耗时数秒。而 Serverless 追求极致的按量付费、瞬间拉起、用完即毁——Tomcat 太胖太慢了。

**演进方向：** Java 阵营现在利用 **GraalVM 编译器** 进行 AOT（提前编译），在打包时把所有反射和配置全部计算好，直接编译成去除了 JVM 和 Tomcat 的纯二进制原生镜像（Native Image），让 Spring Boot 3 或 Quarkus 的启动时间缩短到几十毫秒。

**一句话总结：** 云原生是「轻功流派」，底层利用操作系统的 Epoll 机制（非阻塞 I/O），一个线程就能管几万个网络连接，用极低的内存顶住恐怖的并发海啸。
